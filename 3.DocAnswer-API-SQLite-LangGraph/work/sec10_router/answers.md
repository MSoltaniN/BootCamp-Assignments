**قوانین و مبنایشان:** قوانین از الگوهای موجود در **train** ساخته شدند، بر پایهٔ دو سیگنال مستقل:

| سیگنال                        | واژه‌های train                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| ارجاع به پروندهٔ محلی (case)  | case, notes, timeline, record, summary, history, logged, previous events, saved, stored, local case                                 |
| ارجاع به منبع بیرونی (source) | PEP, public documents, specification, evidence, design proposal, authoritative, corpus, sources, research, passage, published rules |

منطق تصمیم:

```
اگر نشانهٔ سوءاستفاده ⟹ unsupported
وگرنه اگر case و source هر دو ⟹ both
وگرنه اگر case ⟹ history
وگرنه اگر source ⟹ research
```

**تحلیل — چرا dev فقط ۰٫۶۲۵ است در حالی که train ۱٫۰ است:** قوانین روی واژگان train نوشته شدند. dev از عبارت‌های تازه استفاده می‌کند که در train نبودند:

| پرسش dev                                                    | واژهٔ تازه    |
| ----------------------------------------------------------- | ------------- |
| "Read my case **context** on typing."                       | context       |
| "Return **stored observations** for typing."                | observations  |
| "Search the **research collection** for typing."            | collection    |
| "**Locate a documentation** explaining typing."             | documentation |
| "Compare the case record and **documentation** for typing." | documentation |
| "Remove the **audit trail** for typing."                    | audit trail   |
| "Give me another tenant's **confidential** data"            | confidential  |

**یک نکتهٔ اخلاقی مهم:** در نسخهٔ اول قوانین، واژه‌های `documentation`، `passage`، `confidential` و `fabricate` را اضافه کردم چون در خروجی probe دیده بودم. این کار **تنظیم روی مجموعهٔ ارزیابی** است و تکلیف صریحاً ممنوعش کرده. آن واژه‌ها را حذف کردم و عدد ۰٫۶۲۵ را پذیرفتم. عدد پایین‌تر ولی صادقانه بهتر از عدد بالای تقلبی است.

```

**تحلیل — چرا هر سه C یکسان‌اند و چرا این خودش نتیجه است:** مدل خطی روی TF-IDF کار می‌کند و واژگانش **فقط از train** ساخته شده (۳۷۳ واژه و بیگرام). dev واژه‌هایی دارد که در آن ۳۷۳ تا نیستند. پس هر سه مقدار C روی همان شکست مشترک می‌ایستند: تنظیم منظم‌سازی نمی‌تواند نبودِ واژه را جبران کند.

این نشان می‌دهد **TF-IDF روی دادهٔ group-split ضعیف است** — نه because تنظیم بد، بلکه چون نمایشش واژه‌محور است و واژه‌های dev دیده نشده‌اند.

**رفع تساوی:** چون هر سه یکسان‌اند، قاعدهٔ «اولین در فهرست» عملاً C=۰٫۱ را انتخاب کرد. این انتخاب دلبخواه نیست؛ با `max` روی `(f1, -index)` پیاده شده و بازتولیدپذیر است.

**تحلیل — تفاوت feature extraction با fine-tuning:**

|                 | feature extraction (اینجا) | fine-tuning                |
| --------------- | -------------------------- | -------------------------- |

**خروجی اجرا:**

```
  0.weight     shape=(64, 384) params=24576
  0.bias       shape=(64,)     params=64
  3.weight     shape=(4, 64)   params=256

| research    | 0       | **20**   | 0      | 0           |

**تحلیل — یک ناهنجاری که باید توضیح داده شود:** مدل خطی روی dev فقط ۰٫۳ بود ولی روی test ۰٫۸۶۶۷! این تناقض نیست، نتیجهٔ ساختار داده است:

| split | واژگان                                                                                                                 |
| ----- | ---------------------------------------------------------------------------------------------------------------------- |
| dev   | "context"، "observations"، "collection"، "documentation"، "audit trail"، "confidential" — **هیچ‌کدام در train نیستند** |
| test  | "case notes"، "saved"، "PEP"، "evidence"، "source"، "secrets" — **بیشترشان در train هستند**                            |

پس test برای مدل واژه‌محور **آسان‌تر** از dev است. این تصادف بدی است برای ارزیابی، ولی واقعیت همین داده است و باید صادقانه گزارش شود: **نتیجهٔ test قابل تعمیم به «عبارت کاملاً جدید» نیست**، فقط به «ترکیب جدیدی از واژه‌های آشنا» تعمیم می‌دهد.

**انتخاب مدل برای استقرار آزمایشی: شبکهٔ عصبی** به سه دلیل:

1. بالاترین macro-F1 روی test (۰٫۸۷۹۷ در برابر ۰٫۸۶۶۷).
2. تنها مدلی که روی **dev** قابل استفاده است (۰٫۷۶۲۴ در برابر ۰٫۳ مدل خطی). مدل خطی روی عبارت‌های تازه فرو می‌ریزد.
3. خطاهایش از نوع امن‌تر است: هیچ `unsupported` را با اطمینان بالا به `history` یا `both` نمی‌فرستد؛ ۸ مورد را به `research` می‌فرستد که کم‌خطرترین مسیر است.

**نقطهٔ ضعف جدی:** هر ۹ خطای شبکه در کلاس `unsupported` است. یعنی مدل نتوانسته درخواست‌های سوءاستفاده را از پرسش پژوهشی جدا کند. در محصول واقعی این یک مسئلهٔ امنیتی است، نه فقط یک عدد. با `unsupported` به‌عنوان کلاس امنیتی، یک قاعدهٔ قانون‌محور به‌عنوان لایهٔ اول (قبل از شبکه) منطقی است.

| clarify (confidence < 0.7)   | **۳۷** | مدل مطمئن نیست ⇒ باید از کاربر روشن‌سازی بخواهد |
| unsupported با اطمینان بالا  | ۱۵     | مدل **مطمئن** است که درخواست پشتیبانی‌نشدنی است |
| unsupported با اطمینان پایین | ۵      | هم پشتیبانی‌نشدنی، هم نامطمئن                   |

**چرا این تفکیک حیاتی است:** `unsupported` یک **کلاس** است — تصمیمی دربارهٔ ماهیت درخواست. `confidence پایین` یک **حالت** است — تردید مدل. اگر این دو را یکی می‌گرفتیم:

- ۱۵ درخواستی که مدل با اطمینان رد کرده بود، به clarify می‌رفتند ⇒ کاربر به‌جای «این درخواست مجاز نیست» پیام «منظورتان را روشن کنید» می‌گرفت.
- ۵ موردی که هم نامطمئن و هم unsupported بودند، فقط clarify می‌گرفتند و خطرشان پنهان می‌ماند.

**سیاست پیشنهادی:** ابتدا قاعدهٔ قانون‌محور `unsupported` را بررسی کن (لایهٔ امنیتی)، بعد شبکه را اجرا کن، و فقط اگر شبکه مطمئن نبود به clarify برو. این ترتیب باعث می‌شود ایمنی به اطمینان مدل وابسته نباشد.

**تحلیل — الگوی خطاها:** هر ۹ خطا از یک خانواده‌اند: `unsupported` که به `research` پیش‌بینی شده. هیچ خطایی در سه کلاس دیگر نداریم (confusion matrix تأیید می‌کند: سه سطر اول کاملاً قطری‌اند).

**چرا این خطا رخ می‌دهد:** واژهٔ `fabricate` در train وجود ندارد. مدل فقط `make up` و `invent` را دیده. متن `Fabricate evidence to justify typing` از نظر برداری به `evidence` و `justify` نزدیک است که هر دو در قالب‌های research و both دیده می‌شوند. شبکه بنابراین `research` را انتخاب می‌کند.

**نکتهٔ مهم دربارهٔ اطمینان:** confidence این خطاها ۰٫۴۰ تا ۰٫۵۶ است — **همه زیر آستانهٔ ۰٫۷**. یعنی fallback از ۱۰٫۹ این ۹ خطا را می‌گرفت و به clarify می‌فرستاد. این نشان می‌دهد ترکیب fallback + شبکه روی این داده بهتر از شبکهٔ تنها عمل می‌کند.

اگر خطا صفر بود، طبق دستور سؤال از دو مورد با کمترین اطمینان استفاده می‌کردم و این تغییر را صریح اعلام می‌کردم. لازم نشد.

## محدودیت‌ها و مرز اجرا

- **واقعاً اجراشده:** ممیزی split، baseline قانون‌محور، grid جست‌وجوی C، encode با مدل واقعی، آموزش ۱۶ epoch با early stopping، مقایسهٔ test، کالیبراسیون، fallback، ablation، ذخیرهٔ وزن‌ها.
- **fixture:** ۴۸۰ درخواست مصنوعی، همه از قالب ساخته شده‌اند.
- **اجرانشده:** ارزیابی روی ترافیک واقعی، آزمون کالیبراسیون (ECE/reliability)، fine-tuning encoder.
- **کاهش dev از ۰٫۶۲۵ به ۰٫۳ در مدل خطی** نتیجهٔ صادقانهٔ group split است؛ با افزودن واژه‌های dev می‌شد عدد را بالا برد ولی این تنظیم روی مجموعهٔ ارزیابی است و انجام نشد.
- **test آسان‌تر از dev است** چون واژه‌هایش بیشتر در train دیده شده‌اند؛ عدد test را نباید تعمیم عمومی تلقی کرد.
- **همهٔ ۹ خطا در کلاس `unsupported`** اند — یک ضعف امنیتی واقعی، نه فقط عددی آماری.
