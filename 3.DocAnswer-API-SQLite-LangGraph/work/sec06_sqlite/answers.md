## زیرسؤال ۶٫۱

**فیلدهای خواسته‌شده و پاسخ دقیق:**

| فیلد کارت          | پاسخ       |
| ------------------ | ---------- |
| آیا اتصال موفق شد؟ | **بله**    |
| نسخهٔ SQLite       | **3.45.3** |

**چرا این کار:** پیش از هر آزمون دیگری باید ثابت شود فایل باز می‌شود، `PRAGMA foreign_keys` واقعاً روشن است و کوئری ساده جواب می‌دهد.

**خروجی اجرا:**

```
connected: True
PRAGMA foreign_keys = 1
SELECT 1 -> 1
sqlite_version(): 3.45.3
connection timeout: 5.0 s
missing-file handling: FileNotFoundError: database file not found: ...\does_not_exist.sqlite
```

**تحلیل:** نکتهٔ اصلی این است که `PRAGMA foreign_keys=ON` **به‌ازای هر اتصال** اعمال می‌شود، نه یک بار برای همیشه روی فایل. اگر آن را فراموش کنی، SQLite بی‌صدا کلید خارجی را نادیده می‌گیرد و ۶٫۳ ظاهراً «قبول» می‌شود بدون اینکه چیزی واقعاً قید شده باشد. به همین دلیل `connect()` در [`work/_common/db.py`](../_common/db.py) همیشه این PRAGMA را اجرا می‌کند.

برای فایل ناموجود، خطای قابل فهم گزارش شد و هیچ موفقیت ساختگی چاپ نشد. `timeout=5.0` هم گذاشته شد تا قفل طولانی به انتظار بی‌پایان تبدیل نشود.

## زیرسؤال ۶٫۲

**فیلدهای خواسته‌شده و پاسخ دقیق:**

| فیلد کارت       | پاسخ    |
| --------------- | ------- |
| تعداد کاربران   | **20**  |
| تعداد پرونده‌ها | **120** |

**چرا این کار:** جدول‌های قراردادی با کلید اصلی و خارجی ساخته شوند و seed دوباره‌پذیر باشد.

**خروجی اجرا:**

```
source users: 20 | source cases: 120
seed run 1: users=20 cases=120
seed run 2: users=20 cases=120
rerun created no duplicates
```

**تحلیل — چرا idempotent است:** هر درج با `INSERT ... ON CONFLICT(...) DO UPDATE` انجام می‌شود، نه `INSERT` ساده. بنابراین اجرای دوباره رکورد جدید نمی‌سازد، فقط فیلدهای موجود را به‌روز می‌کند. شمارش نهایی از **خود فایل** خوانده شد، نه از دیتاست — همان چیزی که کارت می‌خواهد.

شش جدول قراردادی ساخته شد: `users`, `cases`, `sessions`, `messages`, `documents`, `chunks`. کلیدهای خارجی و ایندکس‌ها در [`work/_common/db.py`](../_common/db.py) تعریف شده‌اند و اسکریپت seed در همین پوشه است.

| فیلد کارت                    | پاسخ    |
| ---------------------------- | ------- |

**خروجی اجرا:**

```
IntegrityError: FOREIGN KEY constraint failed
sessions before/after: 0 0
whole transaction rolled back: True
```

**تحلیل:** ترتیب عمدی است: اول یک جلسهٔ **معتبر** درج شد، بعد پیام با `session_id` نامعتبر. جلسهٔ اول به‌تنهایی درست بود، ولی چون پیام شکست خورد، کل تراکنش برگشت و جلسه هم حذف شد. تعداد جلسات قبل و بعد هر دو **۰** است — یعنی اتمیک بودن تراکنش واقعاً کار می‌کند، نه فقط پیام خطا.

## زیرسؤال ۶٫۶

**فیلد خواسته‌شده و پاسخ دقیق — جدول مالک، دیگران و مدیر:**

| کاربر | نقش     | رابطه با `C-001` | وضعیت   |
| ----- | ------- | ---------------- | ------- |
| U-002 | student | مالک پرونده      | **200** |
| U-003 | student | دانشجوی دیگر     | **403** |
| U-000 | admin   | مدیر             | **200** |

**چرا این کار:** منطق مالکیت باید در لایهٔ داده آزموده شود، چون همان adapter را API نهایی مصرف می‌کند.

**تحلیل:** `SQLiteAdapter.read_case` مالکیت را از خود دیتابیس می‌خواند، نه از ورودی کاربر. دو مسیر مجوز جدا هستند: **مالکیت** (`owner_id == user_id`) و **نقش مدیر** (`role == 'admin'`). اگر فقط یکی را می‌ساختیم، یا مدیر از پروندهٔ خودش محروم می‌شد یا هر دانشجو با نقش‌بازی به همه‌چیز دست می‌یافت.

ترتیب بررسی هم مهم است: ابتدا هویت (۴۰۱ اگر کاربر ناشناخته)، بعد وجود پرونده (۴۰۴)، و در آخر مجوز (۴۰۳). این ترتیب باعث می‌شود پاسخ خطا اطلاعات اضافی لو ندهد.

## زیرسؤال ۶٫۸

**فیلدهای خواسته‌شده و پاسخ دقیق:**

| فیلد کارت                               | پاسخ    |
| --------------------------------------- | ------- |
| تعداد اسناد پس از دو اجرا               | **24**  |
| آیا بردارها در همین فایل ذخیره شده‌اند؟ | **بله** |

**خروجی اجرا:**

```
manifest documents: 24
embedding model: sentence-transformers/all-MiniLM-L6-v2 | dim: 384 | max_seq_length: 256
upsert run 1: documents=24 chunks=24
upsert run 2: documents=24 chunks=24
vector bytes per chunk: 1536 = 1536
model metadata rows complete: True
```

**تحلیل:** دو اجرای متوالی UPSERT تعداد را از ۲۴ بالاتر نبرد. بردارها به‌صورت `BLOB` از ۳۸۴ عدد `float32` ذخیره شدند: `384 × 4 = 1536` بایت — همان عددی که در فایل مشاهده شد. `model_id` و `model_revision` برای همهٔ chunkها پر است.

**یک باگ واقعی که در همین مرحله پیدا و رفع شد:** اولین اجرا در بررسی خودکار روی `embedding_dimensions` شکست خورد. علت این بود که `model.encode("یک رشته")` آرایه‌ای با شکل `(384,)` برمی‌گرداند، ولی `model.encode(["یک رشته"])` شکل `(1, 384)` می‌دهد. کد اول `vec[0]` را برمی‌داشت و در نتیجه فقط یک عدد float را در BLOB می‌نوشت. اصلاح: همهٔ متن‌ها در یک batch کدگذاری شدند و شکل ماتریس با `assert matrix.shape == (24, 384)` کنترل شد. این دقیقاً همان دلیلی است که سؤال می‌گوید پیش از ارسال، بررسی خودکار را اجرا کن.

**محدودیت صریح:** این ۲۴ chunk موقت و یک-per-document هستند تا فایل معتبر شود. بخش ۷ با tokenizer همان مدل، chunkهای ۲۲۰/۴۰ توکنی می‌سازد و جای این‌ها را می‌گیرد.

```
login scopes: ['openid', 'email', 'profile']

  "name": "__Host-day3_session",
  "httponly": true,
  "secure": true,
  "samesite": "Lax",

```

**تحلیل — چرا هر ویژگی:** `HttpOnly` جلوی خواندن کوکی با JavaScript (و در نتیجه سرقت با XSS) را می‌گیرد؛ `Secure` ارسال روی HTTPS غیررمز را ممنوع می‌کند؛ `SameSite=Lax` درخواست‌های POST بین‌سایتی (CSRF) را می‌بندد ولی ریدایرکت ورود را نمی‌شکند. پیشوند `__Host-` مرورگر را مجبور می‌کند کوکی را host-only و بدون `Domain` نگه دارد.

**رضایت جدا برای گزارش ایمیلی:** در `auth_config.json` یک بلوک مستقل هست که `requires_explicit_consent: true` دارد و `disabling_keeps_app_working: true`. یعنی کمبود رضایت، برنامه را از کار نمی‌اندازد و ارسال پنهانی هم رخ نمی‌دهد — همان قید ۳٫۴.

هیچ client secret واقعی در artifact نیست؛ فقط نام متغیرهای محیطی ذکر شده و `client_secret_in_artifact: false` در فایل ثبت است.

## محدودیت‌ها و مرز اجرا

- **واقعاً اجراشده:** ساخت و seed دیتابیس، آزمون‌های FK و rollback، injection، ایندکس و plan، ذخیرهٔ بردار ۳۸۴بعدی با مدل محلی، اعتبارسنجی توکن، پاک‌سازی ۴۸۰۰ رویداد، اجرای `check_day3_db.py` با هر سه کد خروج.
- **fixture:** کاربران و پرونده‌های مصنوعی، توکن‌های امضاشده، `TEST-ONLY-SECRET`، `HS256` به‌جای Google.
- **اجرانشده:** ورود زندهٔ Google، PostgreSQL، استقرار شبکه‌ای.
- **کار باقی‌مانده:** ۲۴ chunk فعلی یک-per-document و موقت‌اند؛ بخش ۷ آن‌ها را با chunkهای ۲۲۰/۴۰ توکنی جایگزین می‌کند. تا وقتی آن مرحله اجرا نشود، عدد `chunks` برابر `documents` است و همینطور معتبر می‌ماند (بررسی‌گر `n_chunks >= max(24, n_docs)` می‌خواهد).
