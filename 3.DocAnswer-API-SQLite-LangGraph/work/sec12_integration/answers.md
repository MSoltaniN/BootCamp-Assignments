/api/health: {'status': 'ok', 'engine': 'sqlite', 'users': 20, 'cases': 120, 'chunks': 1286, 'synthetic': True}

**تحلیل:** موتور دیتابیس در پاسخ `/api/health` صریحاً `sqlite` است — همان چیزی که سؤال می‌خواهد گزارش شود. هیچ PostgreSQL یا Docker در مسیر نیست.

شمارش‌ها از **خود فایل** خوانده می‌شوند، نه از متغیر: ۲۰ کاربر، ۱۲۰ پرونده، ۱۲۸۶ chunk.

**یک باگ واقعی که در همین مرحله رخ داد و رفع شد:** `TestClient` توابع sync را در thread کارگر اجرا می‌کند، و شیء `sqlite3.Connection` به thread سازندهٔ خودش بسته است. اجرای اول با `ProgrammingError: SQLite objects created in a thread can only be used in that same thread` شکست خورد. اصلاح: یک اتصال با `check_same_thread=False` و یک `threading.Lock` برای هم‌زمانی. این را باید صریح گفت، چون در محصول واقعی باید از connection pool استفاده شود، نه یک اتصال قفل‌دار.

**تحلیل:** endpoint پاسخ سه کار انجام می‌دهد:

| مرحله               | چه می‌کند                                                      |

```

```

**تحلیل — دفاع دوگانه:**

| لایه   | مکانیزم                          | چرا هر دو لازم‌اند                                    |
| ------ | -------------------------------- | ----------------------------------------------------- |
| سرور   | `escape_html` روی هر متن         | حتی اگر JS اجرا نشود، HTML امن است                    |
| کلاینت | `textContent` به‌جای `innerHTML` | حتی اگر escape فراموش شود، مرورگر متن را اجرا نمی‌کند |

`innerHTML` **صفر** بار استفاده شده. متن پاسخ از یک `<script type="application/json">` خوانده می‌شود که در آن `<` و `>` به `\u003c` و `\u003e` تبدیل شده‌اند تا `</script>` تگ را زودتر نبندد.

**یک تله در ابزار خودم:** تست اولیه به‌دنبال رشتهٔ `<script>alert` در فایل می‌گشت و نتیجه `False` بود. علت این نبود که escape کار نمی‌کند، بلکه **ابزار نوشتن فایل، entityهای HTML را در سورس decode می‌کرد** و رشتهٔ تست به `<script>alert` تبدیل می‌شد. اصلاح: رشتهٔ مورد انتظار از code point ساخته می‌شود (`chr(38) + "lt;..."`). همچنین بررسی شد که escape **دوباره** انجام نشده باشد (`&lt;` = False)، وگرنه کاربر به‌جای متن، `<script>` می‌دید.

**تحلیل — چرا هر فایل:** چهار فایل اصلی تحویل (نوت‌بوک در مرحلهٔ مونتاژ جدا ساخته می‌شود) به‌همراه نمای HTML و راهنمای بازتولید. برای هر فایل `bytes` و `sha256` کامل ثبت شد تا تغییر بعدی قابل تشخیص باشد.

## محدودیت‌ها و مرز اجرا

- **واقعاً اجراشده:** API نهایی با `TestClient`، چهار مسیر منفی، idempotency روی قید یکتایی واقعی، نمای HTML با escape، بازسازی ۸۰۰ trace، هشت کنترل gate، اجرای checker با ۲۲ بررسی، manifest با hash.
- **fixture:** کاربران، پرونده‌ها، رویدادها، حمله‌ها، قیمت‌ها، `X-User-ID`.
- **اجرانشده:** استقرار زنده، ورود Google، LLM پولی، PostgreSQL، OCR.
- **تأخیر ۴۲۹۹ ms مصنوعی است** و مجموع سادهٔ گام‌هاست، نه تأخیر سرتاسری واقعی.
- **اتصال دیتابیس تک‌نمونه با قفل** برای این fixture کافی است؛ محصول واقعی به connection pool نیاز دارد.
- **دادهٔ test هرگز دیده نشد**؛ هیچ عددی در این بخش عملکرد test را توصیف نمی‌کند.
