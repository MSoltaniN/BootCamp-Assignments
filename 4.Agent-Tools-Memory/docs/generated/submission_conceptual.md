# برگهٔ ارسال پاسخ — بخش‌های ۱ تا ۴

پاسخ‌داده‌شده: **48** زیرسؤال از ۱۴۴

> هر پاسخ دو بخش دارد: مقدار فیلد (گزینه) و دلیل. گزینه را از فهرست فرم انتخاب کن و دلیل را در فیلد «دلیل انتخاب» بگذار.

---

## بخش 1 — انتخاب معماری و مرز ایجنت

### 1.1

**سؤال:** مسیر استخراج، اعتبارسنجی و گزارش از پیش مشخص است و قانون امتیازدهی قطعی است. نقطهٔ شروع مناسب چیست؟

**پاسخ:** `Workflow قطعی`

**دلیل انتخاب:** مسیر استخراج، اعتبارسنجی و گزارش از پیش تعریف شده و قانون امتیازدهی قطعی است؛ اسلاید ۴ (Workflow vs Agent) برای همین حالت می‌گوید «قانون کسب‌وکار قطعی است ← Agent نسازید» و «ساده‌ترین راه حلی که کار می‌کند» کافی است. Agent خودمختار و شبکهٔ ده Agent پیچیدگی بی‌توجیه اضافه می‌کنند و حذف اعتبارسنجی کنترل را از بین می‌برد.

### 1.2

**سؤال:** تعداد جستجوها از قبل معلوم نیست و نتیجهٔ هر ابزار قدم بعدی را تغییر می‌دهد. کدام معماری با این نیاز سازگارتر است؟

**پاسخ:** `Agent با حلقهٔ محدود`

**دلیل انتخاب:** دقیقاً دو شرط «Agent بسازید وقتی...» در اسلاید ۴ برقرار است: تعداد قدم‌ها از قبل معلوم نیست و مسیر به نتیجهٔ هر قدم بستگی دارد. صف بدون منطق تصمیم و prompt ثابت نمی‌توانند مسیر را بر اساس نتیجهٔ ابزار عوض کنند و CSS ربطی به معماری تصمیم ندارد.

### 1.3

**سؤال:** سامانه فقط یک رزومه را خلاصه می‌کند و هیچ ابزار یا حافظه‌ای ندارد. در مقیاس پیچیدگی اسلاید ۳ چه سطحی است؟

**پاسخ:** `L0 ساده`

**دلیل انتخاب:** سامانه یک ورودی می‌گیرد و یک خروجی می‌دهد، بدون ابزار، حافظه، RAG یا حلقه. اسلاید ۴ این را «LLM ساده: یک ورودی، یک خروجی» یعنی L0 می‌نامد. چون ابزار و حافظه ندارد به L1 نمی‌رسد و چون حلقهٔ تصمیم ندارد L3 نیست.

### 1.4

**سؤال:** مدل همراه RAG و حافظه دارد ولی ترتیب بازیابی و پاسخ را کد ثابت مشخص می‌کند. دقیق‌ترین توصیف چیست؟

**پاسخ:** `Augmented LLM در یک Workflow`

**دلیل انتخاب:** داشتن RAG و حافظه سطح L1 (Augmented LLM) می‌سازد، اما چون ترتیب بازیابی و پاسخ را کد ثابت مشخص می‌کند، مسیر در سطح L2 قفل شده است؛ اسلاید ۴ برای L2 می‌گوید «مسیر را کد تعیین می‌کند». پس دقیق‌ترین توصیف، L1 درون L2 است؛ صرفِ RAG مدل را خودمختار نمی‌کند.

### 1.5

**سؤال:** در حلقهٔ ReAct کدام مؤلفه واقعاً اثر ابزار را اجرا می‌کند؟

**پاسخ:** `کد dispatcher پس از اعتبارسنجی`

**دلیل انتخاب:** اسلاید ۵ در حلقهٔ ReAct دستور `result = run_tool(call.name, call.args)  # validated` را نشان می‌دهد و اسلاید ۷ صریح است: «مدل فقط می‌گوید این ابزار را با این پارامترها صدا بزن؛ کد شما اجرا می‌کند». متن پاسخ مدل و نام ابزار در prompt فقط قصد را بیان می‌کنند و اثر واقعی ندارند.

### 1.6

**سؤال:** مدل پس از هر نتیجه دوباره همان فراخوانی با همان آرگومان را تکرار می‌کند. کدام کنترل مستقیم‌تر است؟

**پاسخ:** `اثر انگشت عمل تکراری همراه سقف قدم`

**دلیل انتخاب:** اسلاید ۵ «تشخیص حلقهٔ تکراری و Timeout» را از شروط توقف صریح می‌داند. تکرار همان فراخوانی با همان آرگومان یعنی مدل در حلقه افتاده؛ اثر انگشت عمل آن را مستقیم تشخیص می‌دهد و سقف قدم جلوی ادامه را می‌گیرد. افزایش context یا دما علت را رفع نمی‌کند و حذف trace فقط شواهد را از بین می‌برد.

### 1.7

**سؤال:** پاسخ نهایی درست است ولی مدل پیش از آن یک پروندهٔ غیرمجاز را خوانده است. ارزیابی درست چیست؟

**پاسخ:** `نتیجه موفق ولی مسیر نامعتبر`

**دلیل انتخاب:** اسلاید ۱۶ می‌گوید هم نتیجه و هم مسیر (Trajectory) سنجیده می‌شود. خواندن پروندهٔ غیرمجاز نقض scope است، حتی اگر پاسخ نهایی درست باشد؛ پس «موفقیت کامل» غلط است و این خطا صرفاً ظاهری نیست.

### 1.8

**سؤال:** ابزارها همگی خواندنی‌اند ولی مدل خروجی با توصیهٔ استخدام خودکار تولید می‌کند. چه چیزی کم است؟

**پاسخ:** `کنترل دامنه و اعتبارسنجی خروجی`

**دلیل انتخاب:** اسلاید ۱۴ برای لایهٔ خروجی «Structured Output: خروجی Agent فقط JSON معتبر با فیلدهای مشخص» را الزام می‌کند. توصیهٔ استخدام خودکار خارج از دامنهٔ مجاز است و باید در schema خروجی رد شود، نه با قضاوت متنی. ابزار نوشتن یا بعد بردار بیشتر این شکاف را پر نمی‌کند.

### 1.9

**سؤال:** وظیفهٔ جدید را یک Agent با سه ابزار درست انجام می‌دهد. اولین تصمیم برای افزودن پنج متخصص چیست؟

**پاسخ:** `مقایسهٔ قابل سنجش با baseline تک‌ایجنت`

**دلیل انتخاب:** اسلاید ۱۰ می‌گوید «اول یک Agent خوب بسازید» و چند-Agent فقط وقتی توجیه دارد که «Eval نشان دهد یک Agent از پس کار برنمی‌آید». پس اولین تصمیم ساختن baseline قابل سنجش است؛ افزودن فوری نقش‌ها یا انتخاب با تعداد نقش توجیه تجربی ندارد و حذف baseline مقایسه را ناممکن می‌کند.

### 1.10

**سؤال:** یک ابزار timeout می‌شود اما عملیات آن شاید در سرور انجام شده باشد. برای retry یک نوشتن چه قیدی لازم است؟

**پاسخ:** `کلید idempotency و بازیابی وضعیت`

**دلیل انتخاب:** اسلاید ۳ می‌گوید «کلید Idempotency جلوی اجرای دوباره را می‌گیرد». timeout یعنی وضعیت نامعلوم است؛ فرض شکست قطعی می‌تواند نوشتن دوباره بسازد و ارسال با کلید تازه همان اثر تکرار را تأیید می‌کند. خاموش‌کردن audit هم نقض جداگانه است.

### 1.11

**سؤال:** سقف هزینه پس از انجام فراخوانی گران بررسی می‌شود. ایراد اصلی چیست؟

**پاسخ:** `کنترل پیش از اقدام انجام نشده است`

**دلیل انتخاب:** اسلاید ۵ می‌گوید «سقف هزینه، سقف قدم، Timeout را همیشه صریح بنویسید». اگر سقف هزینه پس از فراخوانی بررسی شود، بودجه بعد از خرج شدن سنجیده می‌شود و کنترل پیشگیرانه نیست. نام مدل، نمودار و فشردگی context با این نقص ارتباطی ندارند.

### 1.12

**سؤال:** یک worker پاسخ ناقص را با قطعیت به همهٔ نقش‌ها می‌فرستد. کدام خطر معماری رخ می‌دهد؟

**پاسخ:** `شکست زنجیره‌ای`

**دلیل انتخاب:** اسلاید ۱۰ این را «Cascading Failure: خطای یکی به همه می‌رسد» می‌نامد. ارسال پاسخ ناقص با قطعیت به همهٔ نقش‌ها خطا را تکثیر می‌کند. cache miss و context rot این اثر را توضیح نمی‌دهند و consensus با پاسخ ناقص ساخته نمی‌شود.

## بخش 2 — مهندسی context و قرارداد ابزار

### 2.1

**سؤال:** در هر قدم فقط اسناد همان tenant و دپارتمان انتخاب می‌شوند. این اقدام در چهار راهبرد context چیست؟

**پاسخ:** `Select`

**دلیل انتخاب:** انتخاب اینکه کدام سند وارد پنجره شود راهبرد Select است؛ اسلاید ۶: «Select: فقط مرتبط‌ها را وارد کن». فیلتر tenant و دپارتمان در واقع انتخاب زیرمجموعهٔ مجاز پیش از ورود به پنجره است. Isolate مربوط به context جدا برای زیر-Agent است و Compress و Write دربارهٔ حجم و محل نگهداری‌اند.

### 2.2

**سؤال:** نتیجهٔ حجیم ابزار به فایل خارج از پنجره منتقل و فقط شناسه و خلاصه نگه داشته می‌شود. راهبرد اصلی چیست؟

**پاسخ:** `Write`

**دلیل انتخاب:** اسلاید ۶: «Write: بیرون از پنجره ذخیره کن: Scratchpad، فایل یادداشت، State». انتقال نتیجهٔ حجیم به فایل بیرونی و نگه‌داشتن فقط شناسه و خلاصه دقیقاً همین است. Voting و افزایش دما بی‌ربط‌اند و Select مربوط به ورود اطلاعات است نه خروج آن.

### 2.3

**سؤال:** برای کم‌کردن تاریخچه فقط فیلدهای لازم JSON و عدم قطعیت حفظ می‌شوند. این چیست؟

**پاسخ:** `Compress`

**دلیل انتخاب:** اسلاید ۶: «Compress: خلاصه کردن تاریخچه، حذف Tool Resultهای قدیمی، نگه داشتن فقط فیلدهای لازم از JSON». حفظ عدم قطعیت هم شرط کیفیت فشرده‌سازی است. این کار تزریق را رفع نمی‌کند و شواهد را هم کاملاً حذف نمی‌کند.

### 2.4

**سؤال:** worker رزومه را در context جدا می‌خواند و فقط ادعاهای ساختاریافته برمی‌گرداند. راهبرد چیست؟

**پاسخ:** `Isolate`

**دلیل انتخاب:** اسلاید ۶: «Isolate: زیر-Agent با Context تمیز و جدا؛ فقط نتیجهٔ خلاصه برمی‌گردد». خواندن رزومه در context جدا و برگرداندن فقط ادعاهای ساختاریافته همان الگو است. اشتراک کامل history عکس این است و افزایش سطح دسترسی نقض امنیت است.

### 2.5

**سؤال:** پنجرهٔ مدل ۱۲۰۰ واحد و ذخیرهٔ پاسخ ۲۰۰ واحد است. ظرفیت ورودی چیست؟

**پاسخ:** `۱۰۰۰`

**دلیل انتخاب:** ظرفیت ورودی = پنجره منهای ذخیرهٔ پاسخ: ۱۲۰۰ − ۲۰۰ = ۱۰۰۰ واحد. گزینهٔ ۱۲۰۰ کل پنجره است و ذخیرهٔ پاسخ را نادیده می‌گیرد، ۱۴۰۰ از پنجره بیشتر است و ۲۰۰ فقط ذخیرهٔ پاسخ است.

### 2.6

**سؤال:** نام ابزار run_anything و ورودی آن SQL آزاد است. طراحی بهتر چیست؟

**پاسخ:** `تابع محدود با schema و enum مشخص`

**دلیل انتخاب:** اسلاید ۷: «ورودی محدود: enum و اعتبارسنجی؛ نه SQL آزاد». ابزار با SQL آزاد سطح حمله را به کل پایگاه باز می‌کند. نام طولانی‌تر یا عبارت «لطفاً امن باش» در prompt هیچ قید اجرایی نمی‌سازد و رهاکردن ورودی بدترین حالت است.

### 2.7

**سؤال:** مدل tenant را در arguments می‌فرستد و سرور همان مقدار را هویت معتبر می‌گیرد. ایراد چیست؟

**پاسخ:** `اختلاط ورودی مدل با هویت قابل اعتماد`

**دلیل انتخاب:** این نقص قاعدهٔ «tenant فقط از principal» را می‌شکند: اگر سرور مقداری را که مدل در arguments فرستاده هویت معتبر بگیرد، مدل می‌تواند آن را جعل کند. کیفیت tokenizer، ضعف compression و top_k هیچ ارتباطی با مرز هویت ندارند.

### 2.8

**سؤال:** MCP Server در صورت پشتیبانی چه سه نوع قابلیت را ارائه می‌کند؟

**پاسخ:** `Tools و Resources و Prompts`

**دلیل انتخاب:** اسلاید ۷ صریح است: «هر Server سه چیز ارائه می‌دهد: Tools، Resources، Prompts». گزینه‌های دیگر یا مفاهیم آموزش مدل‌اند (train/dev/test) یا زیرساخت (GPU، HTTP GET) و ربطی به قابلیت‌های MCP ندارند.

### 2.9

**سؤال:** در stdio واقعی MCP، stdout سرور برای چه چیزی باید رزرو شود؟

**پاسخ:** `پیام‌های پروتکل`

**دلیل انتخاب:** در transport stdio، stdout کانال JSON-RPC است و باید فقط برای پیام‌های پروتکل رزرو شود. هر print اضافی جریان را می‌شکند؛ به همین دلیل لاگ‌ها باید به stderr یا فایل بروند. نمایش رمز اتصال هم نقض امنیتی است.

### 2.10

**سؤال:** کدام گزاره دربارهٔ Function Calling درست است؟

**پاسخ:** `پیشنهاد ابزار توسط مدل باید در برنامه اجرا و اعتبارسنجی شود`

**دلیل انتخاب:** اسلاید ۷: «مدل فقط می‌گوید این ابزار را با این پارامترها صدا بزن؛ کد شما اجرا می‌کند». پس tool call خودکار موفق نیست، JSON مجوز مدیر نمی‌سازد و schema جای RBAC را نمی‌گیرد؛ schema فقط شکل داده را کنترل می‌کند.

### 2.11

**سؤال:** MCP و پیام‌دادن بین متخصص‌ها چه تفاوتی دارند؟

**پاسخ:** `MCP قرارداد دسترسی به قابلیت‌هاست؛ ارتباط agentها مسئلهٔ جداگانه دارد`

**دلیل انتخاب:** اسلاید ۷ دو محور را جدا می‌کند: MCP برای «مدل ↔ ابزار» و A2A («پروتکل گفتگوی Agentها با هم») برای «agent ↔ agent». پس یک JSON داخلی پیاده‌سازی کامل A2A نیست و MCP هم لزوماً ابزار نوشتن نیست.

### 2.12

**سؤال:** سند بازیابی‌شده می‌گوید ابزار انتقال پول را اجرا کن. جایگاه متن چیست؟

**پاسخ:** `دادهٔ نامطمئن بدون اختیار تغییر سیاست`

**دلیل انتخاب:** اسلاید ۱۳ و ۱۴: محتوای برگشتی از ابزار یا سند «داده» است نه «دستور». متن داخل سند بازیابی‌شده نمی‌تواند سیاست را عوض کند یا مجوز بسازد؛ اگر چنین اختیاری داشت، همان تزریق غیرمستقیم رخ داده است.

## بخش 3 — حافظه و الگوهای گردش کار

### 3.1

**سؤال:** اطلاعات تأییدشدهٔ مهارت فرد در چند نشست استفاده می‌شود. نوع حافظه چیست؟

**پاسخ:** `Semantic بلندمدت`

**دلیل انتخاب:** اسلاید ۸: «Semantic: حقایق» — اطلاعات پایدار دربارهٔ فرد که بین نشست‌ها معنا دارد. working memory با پایان session پاک می‌شود و checkpoint فقط وضعیت اجرا را نگه می‌دارد، نه محتوای دانشی.

### 3.2

**سؤال:** یادداشت اینکه در بررسی قبلی چه اتفاقی افتاد بیشتر چیست؟

**پاسخ:** `Episodic`

**دلیل انتخاب:** اسلاید ۸: «Episodic: تجربه‌ها (جلسهٔ هفتهٔ پیش با علی)». یادداشت اینکه در بررسی قبلی چه گذشت ثبت تجربه است، نه حقیقت پایدار و نه روش. Prompt template و Tool schema هم اصلاً حافظه نیستند.

### 3.3

**سؤال:** نسخهٔ روش بازبینی مورد تأیید مدیر در حافظهٔ روش‌ها ذخیره می‌شود. نوع چیست؟

**پاسخ:** `Procedural`

**دلیل انتخاب:** اسلاید ۸: «Procedural: روش‌ها (Prompt و قواعد بهبودیافته)». نسخهٔ تأییدشدهٔ روش بازبینی یک رویه است. Episodic تجربهٔ یک رخداد است و session history فقط تاریخچهٔ گفتگو.

### 3.4

**سؤال:** تاریخچه و نتایج ابزار همین وظیفه تا پایان session نگه داشته می‌شوند. نوع چیست؟

**پاسخ:** `Working memory`

**دلیل انتخاب:** اسلاید ۸ حافظهٔ کوتاه‌مدت را «تاریخچهٔ گفتگو، Tool Resultهای همین وظیفه، Scratchpad» می‌داند و می‌گوید «با پایان Session پاک می‌شود». Semantic دائمی و مجوز ثبت پروفایل تعریف‌های دیگری دارند.

### 3.5

**سؤال:** پس از crash باید از نقطهٔ قبل از تأیید ادامه داد. چه لازم است؟

**پاسخ:** `checkpoint پایدار و شناسهٔ وظیفه`

**دلیل انتخاب:** اسلاید ۸: «وضعیت هر قدم ذخیره شود تا بعد از خطا یا تأیید انسان، از همان جا ادامه دهد (State Machine / Graph)». متغیر Python در RAM با crash از بین می‌رود و prompt بلندتر وضعیت را بازیابی نمی‌کند.

### 3.6

**سؤال:** خروجی استخراج فقط بعد از عبور از schema gate به گزارش می‌رود. الگو چیست؟

**پاسخ:** `Prompt Chaining`

**دلیل انتخاب:** اسلاید ۹: «Prompt Chaining: خروجی هر قدم، ورودی بعدی؛ با Gate بین قدم‌ها». عبور از schema gate پیش از رفتن به گزارش دقیقاً همان gate بین قدم‌هاست. Voting بدون gate و handoff نامحدود این کنترل را ندارند.

### 3.7

**سؤال:** درخواست مالی به ابزار مالی و درخواست بازاریابی به ابزار مربوط می‌رود. الگو چیست؟

**پاسخ:** `Routing`

**دلیل انتخاب:** اسلاید ۹: «Routing: دسته‌بندی ورودی و ارسال به مسیر تخصصی». ارجاع درخواست مالی و بازاریابی به ابزار مربوط همان طبقه‌بندی و مسیردهی است. Compression، Rollback و Parallelization کارهای دیگری می‌کنند.

### 3.8

**سؤال:** دو ارزیابی مستقل مهارت و سیاست هم‌زمان انجام و سپس جمع می‌شوند. الگو چیست؟

**پاسخ:** `Parallelization با sectioning`

**دلیل انتخاب:** اسلاید ۹: «چند زیروظیفه هم‌زمان (Sectioning)». دو ارزیابی مستقل که هم‌زمان اجرا و سپس تجمیع می‌شوند همین الگو را می‌سازند. Voting رأی‌گیری روی یک پرسش است و زنجیرهٔ ترتیبی موازی‌سازی را از دست می‌دهد.

### 3.9

**سؤال:** یک هماهنگ‌کننده بر اساس ورودی تعداد متخصص‌ها را پویا انتخاب می‌کند. الگو چیست؟

**پاسخ:** `Orchestrator–Workers`

**دلیل انتخاب:** اسلاید ۹: «Orchestrator–Workers: Agent اصلی وظایف را پویا تقسیم و نتایج را ترکیب می‌کند». انتخاب پویای تعداد متخصص بر اساس ورودی همان تصمیم هماهنگ‌کننده است. زنجیرهٔ ثابت و cache این انعطاف را ندارند.

### 3.10

**سؤال:** تولیدکننده پیش‌نویس را پس از نقد معتبر حداکثر دو بار اصلاح می‌کند. الگو چیست؟

**پاسخ:** `Evaluator–Optimizer`

**دلیل انتخاب:** اسلاید ۹: «Evaluator–Optimizer: یکی تولید می‌کند، دیگری نقد؛ تا رسیدن به معیار». سقف دو بار اصلاح همان شرط توقف است. ذخیرهٔ بدون بازبینی حلقهٔ بهبود ندارد و handoff بدون مقصد الگو نیست.

### 3.11

**سؤال:** کدام وضعیت بیشترین توجیه را برای چندایجنت دارد؟

**پاسخ:** `نقش‌ها به context و مجوزهای متفاوت نیاز دارند`

**دلیل انتخاب:** اسلاید ۱۰ دو توجیه اصلی چند-Agent را می‌آورد: «Context جدا برای هر نقش» و «نقش‌ها دسترسی متفاوت لازم دارند». اگر همه یک history و یک دسترسی داشته باشند تفکیک نقش ارزشی ندارد؛ نام جذاب‌تر و نبود baseline هم توجیه نیستند.

### 3.12

**سؤال:** پیام worker امضا دارد ولی مقصد و زمان انقضا بررسی نمی‌شود. کدام نقص باقی است؟

**پاسخ:** `بازپخش یا تحویل به نقش نامناسب`

**دلیل انتخاب:** اسلاید ۱۰: «پیام بین Agentها باید احراز و ثبت شود». امضا فقط اصالت را می‌گوید؛ بدون بررسی مقصد و انقضا، پیام معتبر می‌تواند بازپخش شود یا به نقش نادرست برسد. استقلال و trace هم با این نقص تأمین نمی‌شوند.

## بخش 4 — اختیار انسانی و ارزیابی استقرار

### 4.1

**سؤال:** Agent پیشنهاد می‌دهد و کاربر هر اقدام را خودش هدایت می‌کند. طبق اسلاید ۱۰ چه نقشی است؟

**پاسخ:** `L1 Operator`

**دلیل انتخاب:** اسلاید ۱۱: «L1 Operator · اپراتور: کاربر هدایت می‌کند؛ Agent فقط وقتی خواسته شود کمک می‌کند». چون کاربر هر اقدام را خودش هدایت می‌کند و Agent فقط پیشنهاد می‌دهد، L1 است. L3 Consultant آن است که Agent هدایت کند و از کاربر نظر بپرسد.

### 4.2

**سؤال:** Agent پیش‌نویس را مستقل می‌سازد و ثبت حساس فقط پس از تأیید کارشناس است. سطح چیست؟

**پاسخ:** `L4 Approver`

**دلیل انتخاب:** اسلاید ۱۱: «L4 Approver · تأییدکننده: Agent مستقل کار می‌کند؛ کاربر فقط تصمیم‌های پرریسک را تأیید می‌کند». ساخت پیش‌نویس مستقل و تأیید کارشناس فقط برای ثبت حساس همین الگو است. L1 نیست چون Agent مستقل کار می‌کند.

### 4.3

**سؤال:** نسخهٔ جدید کنار کارشناس اجرا می‌شود ولی هیچ اثر واقعی ندارد. مرحلهٔ rollout چیست؟

**پاسخ:** `Shadow`

**دلیل انتخاب:** اسلاید ۱۲: «Shadow: موازی با انسان، مقایسهٔ نتایج» و «Shadow Mode: بدون اثر واقعی». اجرای کنار کارشناس بدون اثر واقعی تعریف shadow است. Canary با نوشتن واقعی روی درصدی از ترافیک کار می‌کند، نه بدون اثر.

### 4.4

**سؤال:** فقط پنج درصد ترافیک به نسخهٔ جدید با کنترل و برگشت می‌رود. روش چیست؟

**پاسخ:** `Canary`

**دلیل انتخاب:** اسلاید ۱۲: «Canary: ۵٪ ترافیک، سپس بیشتر» همراه با «Feature Flag: خاموش کردن فوری» و «Pass Criteria». unit test و افزایش context هیچ‌کدام انتشار تدریجی با قابلیت برگشت نیستند.

### 4.5

**سؤال:** متن مخرب داخل رزومه وارد context می‌شود. نوع injection چیست؟

**پاسخ:** `Indirect`

**دلیل انتخاب:** اسلاید ۱۳: «Indirect: دستور در داده پنهان است: ایمیل، متن پیام صوتی، وب، سند RAG، خروجی ابزار». متن مخرب داخل رزومه که وارد context می‌شود داده است نه ورودی مستقیم کاربر. پس Direct و SQL transaction و Timeout رد می‌شوند.

### 4.6

**سؤال:** Agent هم دادهٔ خصوصی می‌خواند، هم محتوای نامطمئن، هم خروجی بیرونی می‌فرستد. اولویت معماری چیست؟

**پاسخ:** `قطع یا محدودکردن حداقل یک ضلع این ترکیب`

**دلیل انتخاب:** اسلاید ۱۳ «Lethal Trifecta» را تعریف می‌کند: دسترسی به دادهٔ خصوصی + خواندن محتوای غیرقابل اعتماد + توانایی ارتباط بیرونی. با یک تزریق داده نشت می‌کند، پس باید حداقل یک ضلع را قطع کرد. قوی‌کردن جملهٔ system کافی نیست چون هیچ روشی تزریق را ۱۰۰٪ حل نمی‌کند.

### 4.7

**سؤال:** کاربر صد بار بدون خواندن تأیید زده است. چه خطری رخ داده؟

**پاسخ:** `Automation bias`

**دلیل انتخاب:** اسلاید ۱۱: «Automation Bias: انسانی که صد بار تأیید زده، دیگر نمی‌خواند». صد تأیید بدون خواندن یعنی مکانیزم تأیید عملاً از کار افتاده. این خطر کاهش هزینه یا استقلال reviewer نیست و تزریق را هم رفع نمی‌کند.

### 4.8

**سؤال:** مدل یک دستور مخرب را در حافظه ذخیره می‌کند و نشست بعد آن را قانون می‌داند. خطر چیست؟

**پاسخ:** `Memory poisoning`

**دلیل انتخاب:** اسلاید ۸: «Memory Poisoning: اگر Agent از متن ورودی چیزی را در حافظهٔ بلندمدت بنویسد، مهاجم می‌تواند دستوری بکارد که هفته‌ها بعد اجرا شود». ذخیرهٔ دستور مخرب و قانون‌شدن آن در نشست بعد همین حمله است.

### 4.9

**سؤال:** در ارزیابی مسیر، چه چیزی سنجیده می‌شود؟

**پاسخ:** `ابزار و آرگومان و ترتیب مجاز`

**دلیل انتخاب:** اسلاید ۱۶: «Trajectory: ابزار درست، با پارامتر درست، به ترتیب معقول؟». ارزیابی مسیر یعنی همین، مستقل از زیبایی پاسخ یا تعداد پارامتر مدل. زمان کل معیار کارایی است نه معیار مسیر.

### 4.10

**سؤال:** درخواست‌ها ساختار موازی دارند. زمان دیواری هر run از spanها چگونه سنجیده شود؟

**پاسخ:** `بیشینهٔ پایان منهای کمینهٔ شروع`

**دلیل انتخاب:** spanها موازی‌اند، پس جمع همهٔ مدت‌ها زمان دیواری نیست و عدد را متورم می‌کند. زمان دیواری هر run برابر است با دیرترین پایان منهای زودترین شروع. تعداد span و کمترین worker هیچ‌کدام زمان دیواری نمی‌دهند.

### 4.11

**سؤال:** یک گروه فقط سه نمونه دارد و اختلاف کیفیت صفر مشاهده شده است. نتیجهٔ مناسب چیست؟

**پاسخ:** `نمونه برای ادعای برابری کافی نیست`

**دلیل انتخاب:** سه نمونه پایهٔ آماری برای ادعای برابری ندارد؛ نتیجه باید تعریف‌نشده تلقی شود نه «برابری اثبات‌شده». حذف گروه داده را از بین می‌برد و واردکردن gold به ورودی مدل هم نشت برچسب است.

### 4.12

**سؤال:** Agent Card مفید باید چه چیزی را روشن کند؟

**پاسخ:** `مالک و هدف و ابزار و سطح اختیار و معیار ارجاع و بودجه`

**دلیل انتخاب:** اسلاید ۱۷: «یک Agent Card برای هر Agent بنویسید: هدف، مالک، ابزارها و دسترسی‌ها، سطح خودمختاری، شرایط ارجاع به انسان، معیارهای Eval، هزینهٔ مجاز». لوگو، تاریخ ساخت و نام مدل هیچ‌کدام این مسئولیت‌پذیری را نمی‌سازند.
