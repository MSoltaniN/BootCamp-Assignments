--- 1.1
ANSWER : Workflow قطعی
REASON : مسیر استخراج، اعتبارسنجی و گزارش از پیش تعریف شده و قانون امتیازدهی قطعی است؛ اسلاید ۴ (Workflow vs Agent) برای همین حالت می‌گوید «قانون کسب‌وکار قطعی است ← Agent نسازید» و «ساده‌ترین راه حلی که کار می‌کند» کافی است. Agent خودمختار و شبکهٔ ده Agent پیچیدگی بی‌توجیه اضافه می‌کنند و حذف اعتبارسنجی کنترل را از بین می‌برد.

--- 1.2
ANSWER : Agent با حلقهٔ محدود
REASON : دقیقاً دو شرط «Agent بسازید وقتی...» در اسلاید ۴ برقرار است: تعداد قدم‌ها از قبل معلوم نیست و مسیر به نتیجهٔ هر قدم بستگی دارد. صف بدون منطق تصمیم و prompt ثابت نمی‌توانند مسیر را بر اساس نتیجهٔ ابزار عوض کنند و CSS ربطی به معماری تصمیم ندارد.

--- 1.3
ANSWER : L0 ساده
REASON : سامانه یک ورودی می‌گیرد و یک خروجی می‌دهد، بدون ابزار، حافظه، RAG یا حلقه. اسلاید ۴ این را «LLM ساده: یک ورودی، یک خروجی» یعنی L0 می‌نامد. چون ابزار و حافظه ندارد به L1 نمی‌رسد و چون حلقهٔ تصمیم ندارد L3 نیست.

--- 1.4
ANSWER : Augmented LLM در یک Workflow
REASON : داشتن RAG و حافظه سطح L1 (Augmented LLM) می‌سازد، اما چون ترتیب بازیابی و پاسخ را کد ثابت مشخص می‌کند، مسیر در سطح L2 قفل شده است؛ اسلاید ۴ برای L2 می‌گوید «مسیر را کد تعیین می‌کند». پس دقیق‌ترین توصیف، L1 درون L2 است؛ صرفِ RAG مدل را خودمختار نمی‌کند.

--- 1.5
ANSWER : کد dispatcher پس از اعتبارسنجی
REASON : اسلاید ۵ در حلقهٔ ReAct دستور `result = run_tool(call.name, call.args)  # validated` را نشان می‌دهد و اسلاید ۷ صریح است: «مدل فقط می‌گوید این ابزار را با این پارامترها صدا بزن؛ کد شما اجرا می‌کند». متن پاسخ مدل و نام ابزار در prompt فقط قصد را بیان می‌کنند و اثر واقعی ندارند.

--- 1.6
ANSWER : اثر انگشت عمل تکراری همراه سقف قدم
REASON : اسلاید ۵ «تشخیص حلقهٔ تکراری و Timeout» را از شروط توقف صریح می‌داند. تکرار همان فراخوانی با همان آرگومان یعنی مدل در حلقه افتاده؛ اثر انگشت عمل آن را مستقیم تشخیص می‌دهد و سقف قدم جلوی ادامه را می‌گیرد. افزایش context یا دما علت را رفع نمی‌کند و حذف trace فقط شواهد را از بین می‌برد.

--- 1.7
ANSWER : نتیجه موفق ولی مسیر نامعتبر
REASON : اسلاید ۱۶ می‌گوید هم نتیجه و هم مسیر (Trajectory) سنجیده می‌شود. خواندن پروندهٔ غیرمجاز نقض scope است، حتی اگر پاسخ نهایی درست باشد؛ پس «موفقیت کامل» غلط است و این خطا صرفاً ظاهری نیست.

--- 1.8
ANSWER : کنترل دامنه و اعتبارسنجی خروجی
REASON : اسلاید ۱۴ برای لایهٔ خروجی «Structured Output: خروجی Agent فقط JSON معتبر با فیلدهای مشخص» را الزام می‌کند. توصیهٔ استخدام خودکار خارج از دامنهٔ مجاز است و باید در schema خروجی رد شود، نه با قضاوت متنی. ابزار نوشتن یا بعد بردار بیشتر این شکاف را پر نمی‌کند.

--- 1.9
ANSWER : مقایسهٔ قابل سنجش با baseline تک‌ایجنت
REASON : اسلاید ۱۰ می‌گوید «اول یک Agent خوب بسازید» و چند-Agent فقط وقتی توجیه دارد که «Eval نشان دهد یک Agent از پس کار برنمی‌آید». پس اولین تصمیم ساختن baseline قابل سنجش است؛ افزودن فوری نقش‌ها یا انتخاب با تعداد نقش توجیه تجربی ندارد و حذف baseline مقایسه را ناممکن می‌کند.

--- 1.10
ANSWER : کلید idempotency و بازیابی وضعیت
REASON : اسلاید ۳ می‌گوید «کلید Idempotency جلوی اجرای دوباره را می‌گیرد». timeout یعنی وضعیت نامعلوم است؛ فرض شکست قطعی می‌تواند نوشتن دوباره بسازد و ارسال با کلید تازه همان اثر تکرار را تأیید می‌کند. خاموش‌کردن audit هم نقض جداگانه است.

--- 1.11
ANSWER : کنترل پیش از اقدام انجام نشده است
REASON : اسلاید ۵ می‌گوید «سقف هزینه، سقف قدم، Timeout را همیشه صریح بنویسید». اگر سقف هزینه پس از فراخوانی بررسی شود، بودجه بعد از خرج شدن سنجیده می‌شود و کنترل پیشگیرانه نیست. نام مدل، نمودار و فشردگی context با این نقص ارتباطی ندارند.

--- 1.12
ANSWER : شکست زنجیره‌ای
REASON : اسلاید ۱۰ این را «Cascading Failure: خطای یکی به همه می‌رسد» می‌نامد. ارسال پاسخ ناقص با قطعیت به همهٔ نقش‌ها خطا را تکثیر می‌کند. cache miss و context rot این اثر را توضیح نمی‌دهند و consensus با پاسخ ناقص ساخته نمی‌شود.

--- 2.1
ANSWER : Select
REASON : انتخاب اینکه کدام سند وارد پنجره شود راهبرد Select است؛ اسلاید ۶: «Select: فقط مرتبط‌ها را وارد کن». فیلتر tenant و دپارتمان در واقع انتخاب زیرمجموعهٔ مجاز پیش از ورود به پنجره است. Isolate مربوط به context جدا برای زیر-Agent است و Compress و Write دربارهٔ حجم و محل نگهداری‌اند.

--- 2.2
ANSWER : Write
REASON : اسلاید ۶: «Write: بیرون از پنجره ذخیره کن: Scratchpad، فایل یادداشت، State». انتقال نتیجهٔ حجیم به فایل بیرونی و نگه‌داشتن فقط شناسه و خلاصه دقیقاً همین است. Voting و افزایش دما بی‌ربط‌اند و Select مربوط به ورود اطلاعات است نه خروج آن.

--- 2.3
ANSWER : Compress
REASON : اسلاید ۶: «Compress: خلاصه کردن تاریخچه، حذف Tool Resultهای قدیمی، نگه داشتن فقط فیلدهای لازم از JSON». حفظ عدم قطعیت هم شرط کیفیت فشرده‌سازی است. این کار تزریق را رفع نمی‌کند و شواهد را هم کاملاً حذف نمی‌کند.

--- 2.4
ANSWER : Isolate
REASON : اسلاید ۶: «Isolate: زیر-Agent با Context تمیز و جدا؛ فقط نتیجهٔ خلاصه برمی‌گردد». خواندن رزومه در context جدا و برگرداندن فقط ادعاهای ساختاریافته همان الگو است. اشتراک کامل history عکس این است و افزایش سطح دسترسی نقض امنیت است.

--- 2.5
ANSWER : ۱۰۰۰
REASON : ظرفیت ورودی = پنجره منهای ذخیرهٔ پاسخ: ۱۲۰۰ − ۲۰۰ = ۱۰۰۰ واحد. گزینهٔ ۱۲۰۰ کل پنجره است و ذخیرهٔ پاسخ را نادیده می‌گیرد، ۱۴۰۰ از پنجره بیشتر است و ۲۰۰ فقط ذخیرهٔ پاسخ است.

--- 2.6
ANSWER : تابع محدود با schema و enum مشخص
REASON : اسلاید ۷: «ورودی محدود: enum و اعتبارسنجی؛ نه SQL آزاد». ابزار با SQL آزاد سطح حمله را به کل پایگاه باز می‌کند. نام طولانی‌تر یا عبارت «لطفاً امن باش» در prompt هیچ قید اجرایی نمی‌سازد و رهاکردن ورودی بدترین حالت است.

--- 2.7
ANSWER : اختلاط ورودی مدل با هویت قابل اعتماد
REASON : این نقص قاعدهٔ «tenant فقط از principal» را می‌شکند: اگر سرور مقداری را که مدل در arguments فرستاده هویت معتبر بگیرد، مدل می‌تواند آن را جعل کند. کیفیت tokenizer، ضعف compression و top_k هیچ ارتباطی با مرز هویت ندارند.

--- 2.8
ANSWER : Tools و Resources و Prompts
REASON : اسلاید ۷ صریح است: «هر Server سه چیز ارائه می‌دهد: Tools، Resources، Prompts». گزینه‌های دیگر یا مفاهیم آموزش مدل‌اند (train/dev/test) یا زیرساخت (GPU، HTTP GET) و ربطی به قابلیت‌های MCP ندارند.

--- 2.9
ANSWER : پیام‌های پروتکل
REASON : در transport stdio، stdout کانال JSON-RPC است و باید فقط برای پیام‌های پروتکل رزرو شود. هر print اضافی جریان را می‌شکند؛ به همین دلیل لاگ‌ها باید به stderr یا فایل بروند. نمایش رمز اتصال هم نقض امنیتی است.

--- 2.10
ANSWER : پیشنهاد ابزار توسط مدل باید در برنامه اجرا و اعتبارسنجی شود
REASON : اسلاید ۷: «مدل فقط می‌گوید این ابزار را با این پارامترها صدا بزن؛ کد شما اجرا می‌کند». پس tool call خودکار موفق نیست، JSON مجوز مدیر نمی‌سازد و schema جای RBAC را نمی‌گیرد؛ schema فقط شکل داده را کنترل می‌کند.

--- 2.11
ANSWER : MCP قرارداد دسترسی به قابلیت‌هاست؛ ارتباط agentها مسئلهٔ جداگانه دارد
REASON : اسلاید ۷ دو محور را جدا می‌کند: MCP برای «مدل ↔ ابزار» و A2A («پروتکل گفتگوی Agentها با هم») برای «agent ↔ agent». پس یک JSON داخلی پیاده‌سازی کامل A2A نیست و MCP هم لزوماً ابزار نوشتن نیست.

--- 2.12
ANSWER : دادهٔ نامطمئن بدون اختیار تغییر سیاست
REASON : اسلاید ۱۳ و ۱۴: محتوای برگشتی از ابزار یا سند «داده» است نه «دستور». متن داخل سند بازیابی‌شده نمی‌تواند سیاست را عوض کند یا مجوز بسازد؛ اگر چنین اختیاری داشت، همان تزریق غیرمستقیم رخ داده است.

--- 3.4

REASON : اسلاید ۸ حافظهٔ کوتاه‌مدت را «تاریخچهٔ گفتگو، Tool Resultهای همین وظیفه، Scratchpad» می‌داند و می‌گوید «با پایان Session پاک می‌شود». Semantic دائمی و مجوز ثبت پروفایل تعریف‌های دیگری دارند.

--- 3.6

REASON : اسلاید ۹: «Prompt Chaining: خروجی هر قدم، ورودی بعدی؛ با Gate بین قدم‌ها». عبور از schema gate پیش از رفتن به گزارش دقیقاً همان gate بین قدم‌هاست. Voting بدون gate و handoff نامحدود این کنترل را ندارند.

REASON : اسلاید ۹: «Routing: دسته‌بندی ورودی و ارسال به مسیر تخصصی». ارجاع درخواست مالی و بازاریابی به ابزار مربوط همان طبقه‌بندی و مسیردهی است. Compression، Rollback و Parallelization کارهای دیگری می‌کنند.

--- 3.8
ANSWER : Parallelization با sectioning
REASON : اسلاید ۹: «چند زیروظیفه هم‌زمان (Sectioning)». دو ارزیابی مستقل که هم‌زمان اجرا و سپس تجمیع می‌شوند همین الگو را می‌سازند. Voting رأی‌گیری روی یک پرسش است و زنجیرهٔ ترتیبی موازی‌سازی را از دست می‌دهد.

--- 3.9
ANSWER : Orchestrator–Workers
REASON : اسلاید ۹: «Orchestrator–Workers: Agent اصلی وظایف را پویا تقسیم و نتایج را ترکیب می‌کند». انتخاب پویای تعداد متخصص بر اساس ورودی همان تصمیم هماهنگ‌کننده است. زنجیرهٔ ثابت و cache این انعطاف را ندارند.

--- 3.10
ANSWER : Evaluator–Optimizer
REASON : اسلاید ۹: «Evaluator–Optimizer: یکی تولید می‌کند، دیگری نقد؛ تا رسیدن به معیار». سقف دو بار اصلاح همان شرط توقف است. ذخیرهٔ بدون بازبینی حلقهٔ بهبود ندارد و handoff بدون مقصد الگو نیست.

--- 3.11
ANSWER : نقش‌ها به context و مجوزهای متفاوت نیاز دارند
REASON : اسلاید ۱۰ دو توجیه اصلی چند-Agent را می‌آورد: «Context جدا برای هر نقش» و «نقش‌ها دسترسی متفاوت لازم دارند». اگر همه یک history و یک دسترسی داشته باشند تفکیک نقش ارزشی ندارد؛ نام جذاب‌تر و نبود baseline هم توجیه نیستند.

--- 3.12
ANSWER : بازپخش یا تحویل به نقش نامناسب

--- 4.1
ANSWER : L1 Operator
REASON : اسلاید ۱۱: «L1 Operator · اپراتور: کاربر هدایت می‌کند؛ Agent فقط وقتی خواسته شود کمک می‌کند». چون کاربر هر اقدام را خودش هدایت می‌کند و Agent فقط پیشنهاد می‌دهد، L1 است. L3 Consultant آن است که Agent هدایت کند و از کاربر نظر بپرسد.

--- 4.2
ANSWER : L4 Approver
REASON : اسلاید ۱۱: «L4 Approver · تأییدکننده: Agent مستقل کار می‌کند؛ کاربر فقط تصمیم‌های پرریسک را تأیید می‌کند». ساخت پیش‌نویس مستقل و تأیید کارشناس فقط برای ثبت حساس همین الگو است. L1 نیست چون Agent مستقل کار می‌کند.

--- 4.3
ANSWER : Shadow
REASON : اسلاید ۱۲: «Shadow: موازی با انسان، مقایسهٔ نتایج» و «Shadow Mode: بدون اثر واقعی». اجرای کنار کارشناس بدون اثر واقعی تعریف shadow است. Canary با نوشتن واقعی روی درصدی از ترافیک کار می‌کند، نه بدون اثر.

--- 4.4
ANSWER : Canary
REASON : اسلاید ۱۲: «Canary: ۵٪ ترافیک، سپس بیشتر» همراه با «Feature Flag: خاموش کردن فوری» و «Pass Criteria». unit test و افزایش context هیچ‌کدام انتشار تدریجی با قابلیت برگشت نیستند.

--- 4.5
ANSWER : Indirect
REASON : اسلاید ۱۳: «Indirect: دستور در داده پنهان است: ایمیل، متن پیام صوتی، وب، سند RAG، خروجی ابزار». متن مخرب داخل رزومه که وارد context می‌شود داده است نه ورودی مستقیم کاربر. پس Direct و SQL transaction و Timeout رد می‌شوند.

--- 4.6
ANSWER : قطع یا محدودکردن حداقل یک ضلع این ترکیب
REASON : اسلاید ۱۳ «Lethal Trifecta» را تعریف می‌کند: دسترسی به دادهٔ خصوصی + خواندن محتوای غیرقابل اعتماد + توانایی ارتباط بیرونی. با یک تزریق داده نشت می‌کند، پس باید حداقل یک ضلع را قطع کرد. قوی‌کردن جملهٔ system کافی نیست چون هیچ روشی تزریق را ۱۰۰٪ حل نمی‌کند.

--- 4.7
ANSWER : Automation bias
REASON : اسلاید ۱۱: «Automation Bias: انسانی که صد بار تأیید زده، دیگر نمی‌خواند». صد تأیید بدون خواندن یعنی مکانیزم تأیید عملاً از کار افتاده. این خطر کاهش هزینه یا استقلال reviewer نیست و تزریق را هم رفع نمی‌کند.

--- 4.8
ANSWER : Memory poisoning
REASON : اسلاید ۸: «Memory Poisoning: اگر Agent از متن ورودی چیزی را در حافظهٔ بلندمدت بنویسد، مهاجم می‌تواند دستوری بکارد که هفته‌ها بعد اجرا شود». ذخیرهٔ دستور مخرب و قانون‌شدن آن در نشست بعد همین حمله است.

--- 4.9
ANSWER : ابزار و آرگومان و ترتیب مجاز
REASON : اسلاید ۱۶: «Trajectory: ابزار درست، با پارامتر درست، به ترتیب معقول؟». ارزیابی مسیر یعنی همین، مستقل از زیبایی پاسخ یا تعداد پارامتر مدل. زمان کل معیار کارایی است نه معیار مسیر.

--- 4.10
ANSWER : بیشینهٔ پایان منهای کمینهٔ شروع
REASON : spanها موازی‌اند، پس جمع همهٔ مدت‌ها زمان دیواری نیست و عدد را متورم می‌کند. زمان دیواری هر run برابر است با دیرترین پایان منهای زودترین شروع. تعداد span و کمترین worker هیچ‌کدام زمان دیواری نمی‌دهند.

--- 4.11
ANSWER : نمونه برای ادعای برابری کافی نیست
REASON : سه نمونه پایهٔ آماری برای ادعای برابری ندارد؛ نتیجه باید تعریف‌نشده تلقی شود نه «برابری اثبات‌شده». حذف گروه داده را از بین می‌برد و واردکردن gold به ورودی مدل هم نشت برچسب است.

--- 4.12
ANSWER : مالک و هدف و ابزار و سطح اختیار و معیار ارجاع و بودجه
REASON : اسلاید ۱۷: «یک Agent Card برای هر Agent بنویسید: هدف، مالک، ابزارها و دسترسی‌ها، سطح خودمختاری، شرایط ارجاع به انسان، معیارهای Eval، هزینهٔ مجاز». لوگو، تاریخ ساخت و نام مدل هیچ‌کدام این مسئولیت‌پذیری را نمی‌سازند.
