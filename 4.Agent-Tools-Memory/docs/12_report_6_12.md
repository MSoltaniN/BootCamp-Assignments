## بخش ۶: ابزارهای محدود و اتصال واقعی MCP

**ابزارها.** سه ابزار فقط‌خواندنی: `get_employee`، `get_department_context`، `get_evidence`.
برای هر سه، `additionalProperties: false` منتشر می‌شود.

**اعتبارسنجی ورودی.** چهار آزمون منفی، هر چهار رد شد:

| آزمون              | کد خطا           |
| ------------------ | ---------------- |
| نوع نادرست         | `wrong_type`     |
| آرگومان اضافه      | `extra_argument` |
| مقدار خارج از enum | `out_of_enum`    |
| ابزار ناشناخته     | `unknown_tool`   |

هیچ فرمان پوسته‌ای اجرا نشد (`shell_executed: false`).

**جداسازی مستأجر.** هم دسترسی بین‌مستأجری و هم بین‌دپارتمانی بسته شد.

**اتصال MCP واقعی.** زیرفرایند جدا با transport `stdio`:
۳ ابزار، ۱ resource (`policy://finance`)، ۱ prompt (`skills_review`)،
هر سه ردِ امنیتی هم در سطح پروتکل تأیید شد
(`probe_tenant_rejected`، `probe_enum_rejected`، `probe_extra_rejected`).

**نقص مهمی که کشف و بسته شد.** SDK به‌طور پیش‌فرض مدل آرگومان را از امضای تابع می‌سازد و
آرگومان ناشناخته را **بی‌صدا حذف** می‌کند؛ یعنی `tenant` که مدل می‌فرستاد
پذیرفته و بعد دور ریخته می‌شد و مرز مستأجر عملاً بی‌اثر بود.
با `extra="forbid"` روی مدل آرگومان و `model_rebuild(force=True)` و
انتشار `additionalProperties: false` بسته شد.

**شکل خطا.** سه فیلد (`code`، `retryable`، `reason`)؛ هیچ آرگومان خصوصی در خطا بازتاب نمی‌شود.

**اثر انگشت ابزار.** SHA-256 با ۶۴ نویسهٔ هگز؛ با افزودن ابزار تغییر می‌کند.

**دامنهٔ اجرا.** تصمیم‌گیر در این بخش **fixture** است، نه مدل زنده؛
`live_llm_executed: false` صادقانه ثبت شده است.

## بخش ۸: حافظهٔ پایدار و تأیید انسانی

**پایگاه.** شش جدول: `memories`، `profiles`، `approvals`، `writes`، `audit`، `jobs`.
یکپارچگی `ok`، صفر نقض کلید خارجی.

**TTL.** روز ۲۹ زنده (۱)، روز ۳۰ منقضی (۰).

**پایداری.** پس از بستن و بازکردن دوباره، رکورد باقی است.

**مسموم‌سازی حافظه.** رد شد — نوشتن حافظه بدون مدرک معتبر و متن مطابق منبع ممکن نیست.

**جداسازی.** دسترسی به ردیف مستأجر دیگر رد شد، صفر ردیف نشت‌کرده،
ردیف‌های خودی هم‌چنان در دسترس‌اند.

**انتخاب نامزد حافظه.** از ۷۲۰ رویداد، ۳۰۸ نامزد، ۱۰۳ مورد تأییدنشده؛
توزیع تقریباً یکسان بین سه نوع (۱۰۳ / ۱۰۲ / ۱۰۳).

**چرخهٔ تأیید.**

1. `prepare` → نسخه ۰، وقفه ثبت شد.
2. تأیید انسانی → نسخه ۱، یک رویداد audit، نوشتن انجام شد.
3. **بازپخش** → نسخه همان ۱ ماند، audit همان ۱ ماند (تکرار شناسایی شد).
4. محتوای تغییر‌یافته پس از تأیید → رد شد.
5. تأیید کهنه (`base_version != version-1`) → رد شد.
6. تصمیم «رد» → ثبت در audit، نسخه تغییر نکرد (۰ برای رد، ۱ برای تأیید).

**قید بحرانی.** نوشتن با `approval_id` به تأیید گره خورده **و**
`payload_hash` بدنه و `base_version == version-1` هم بررسی می‌شود؛
پس نه تأیید کهنه و نه بدنهٔ ویرایش‌شده قابل استفاده نیست.

**checkpoint.** در پایگاه جدا (`checkpoints`، `writes`).
