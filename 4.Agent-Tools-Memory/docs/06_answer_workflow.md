# روش پاسخ‌دهی

## ۱. سه لایهٔ هر پاسخ

هر زیرسؤال عملی (۵ تا ۱۲) باید هر سه لایه را داشته باشد:

| لایه        | محل                                   | وزن         |
| ----------- | ------------------------------------- | ----------- |
| کد انگلیسی  | سلول کد نوت‌بوک                       | بخشی از ۶۰٪ |
| خروجی اجرا  | خروجی همان سلول (دیده‌شده در نوت‌بوک) | بخشی از ۶۰٪ |
| تحلیل فارسی | سلول مارک‌داون `<div dir="rtl">`      | ۴۰٪         |

اگر یکی غایب باشد، همان سهم از دست می‌رود. عدد بدون کد = ۴۰٪ نمره.

## ۲. ساختار سلول‌های نوت‌بوک

قالب `Student_Template.ipynb` برای هر زیرسؤال سه سلول دارد:

```
[markdown] ### زیرسؤال 5.3
[code]     # Write your implementation here.
[markdown] <div dir="rtl">روش اجرا و تحلیل خود را اینجا بنویسید.</div>
```

- سلول کد: کد پایتون + `print` خروجی‌های کلیدی
- سلول مارک‌داون: تحلیل فارسی، شامل اعداد واقعی و مرز واقعی/fixture

## ۳. الگوی تحلیل فارسی

برای هر سؤال عملی، این پنج بند را بنویس (کوتاه و مشخص):

```
<div dir="rtl">

**روش:** چه کردم و چرا این روش.

**خروجی:** اعداد یا شناسه‌های واقعی که از اجرا آمد.

**تحلیل:** چرا این عدد/نتیجه این معنا را می‌دهد.

**مرز اجرا:** چه چیزی واقعی بود و چه چیزی fixture.

**محدودیت:** چه چیزی این نتیجه را اثبات نمی‌کند.

</div>
```

بند «محدودیت» مهم است چون سایت صریحاً می‌گوید ادعای بیش از شواهد جریمه دارد.

## ۴. استراتژی هر بخش

### بخش ۱–۴ (مفهومی، ۲۴ نمره)

هر سؤال دو فیلد دارد: گزینه + دلیل.

**الگوی دلیل (کوتاه، ۱ تا ۲ جمله):**

> «گزینهٔ X درست است چون قید مسئله می‌گوید ... . گزینهٔ Y رد می‌شود چون ... .»

قاعده: دلیل باید به **قید مسئله** اشاره کند، نه به تعریف عمومی. مثلاً اگر مسئله می‌گوید «تعداد جستجوها از قبل معلوم نیست»، دلیل باید همین را نقل کند.

### بخش ۵ (داده و context، ۸ نمره)

پایهٔ همهٔ بخش‌های بعدی. ابتدا یک ماژول بارگذاری بساز، بعد اعداد را از آن بگیر.

ترتیب: ۵٫۱ (آمار پایه) → ۵٫۲ (scope) → ۵٫۳ و ۵٫۴ (بودجه) → ۵٫۵ (TF-IDF) → ۵٫۶ (redact) → ۵٫۷ (حذف تکرار) → ۵٫۸ (فشرده‌سازی) → ۵٫۹ (context متخصص) → ۵٫۱۰ و ۵٫۱۱ (پروفایل و اعتبارسنجی) → ۵٫۱۲ (پوشش).

### بخش ۶ (MCP، ۸ نمره)

سه فایل: `agent_lab.py` (ابزارها)، `mcp_server.py` (stdio server)، `mcp_probe.py` (client).

**نکتهٔ حیاتی:** `stdout` در stdio فقط برای JSON-RPC است. هر `print` اضافی پروتکل را می‌شکند — لاگ‌ها به `stderr`.

### بخش ۷ (حلقه، ۱۰ نمره)

حلقه با چهار کنترل: سقف قدم، بودجه، تشخیص تکرار (اثر انگشت عمل)، مهلت.

ترتیب بررسی: **قبل از** اثر ابزار، همهٔ کنترل‌ها چک شوند.

### بخش ۸ (حافظه، ۱۰ نمره)

SQLite واقعی. شش جدول با ساختار دقیق `Day4_Grading/README.md`. سپس checker را **جدا** اجرا کن.

`approval` و `write` باید با `payload_hash` و FK به هم bind شوند.

### بخش ۹ (مسیریابی، ۱۰ نمره)

- آموزش روی `train` (۲۰۰)
- تنظیم روی `dev` (۸۰)
- قفل تنظیمات در `locked_router_config.json`
- پیش‌بینی برای `test` (۸۰) — هر شناسه دقیقاً یک‌بار

`request_id`، `template_group` و `audit_group` ویژگی نیستند.

### بخش ۱۰ (امنیت، ۱۰ نمره)

ده خانوادهٔ تهدید. برای هر کدام: ورودی، لایهٔ دفاع، نتیجه، تصمیم.

لایه‌ها: ورودی (اعتبارسنجی) → context (مرز داده/دستور) → ابزار (scope) → خروجی (schema) → حافظه (provenance) → audit.

### بخش ۱۱ (ارزیابی، ۱۰ نمره)

- مقایسهٔ جفت‌شده روی `scenario_id`
- P95 از `duration_ms`، نه جمع span
- accuracy بدون نمونه = تعریف‌نشده، نه صفر
- `audit_group` فقط برای سنجش، نه ویژگی

### بخش ۱۲ (انتشار، ۱۰ نمره)

- `regression_gate` با سه شرط هم‌زمان
- canary → نقض → خاموش‌کردن flag → بازگشت به shadow (با حفظ audit)
- `execution_scope.json` با سه دستهٔ صریح
- `handoff_manifest` + `handoff_check`
- تطبیق hash با `manifest.json` (۱۶/۱۶)
- شمارش پاسخ‌های عملی = ۹۶
