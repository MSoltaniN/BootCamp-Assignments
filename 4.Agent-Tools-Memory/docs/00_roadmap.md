## ۲. ساختار نمره‌دهی

هر بخش از دو لایهٔ متفاوت تشکیل شده و نباید این دو را با هم اشتباه گرفت:

**بخش‌های ۱ تا ۴ (هر کدام ۶ نمره) — مفهومی**

- ۱۲ سناریوی مستقل، هر کدام ۰٫۵ نمره
- هر سؤال: یک گزینه + یک دلیل کوتاه
- معیار: ۶۰٪ گزینهٔ درست، ۴۰٪ کیفیت دلیل

**بخش‌های ۵ تا ۱۲ (۸ یا ۱۰ نمره) — عملی**

- ۸ سؤال ۰٫۵ نمره‌ای + ۴ سؤال ۱ نمره‌ای
- هر سؤال چند فیلد دارد: عدد، بله/خیر، و یک «روش اجرا و تحلیل»
- معیار: ۶۰٪ روش/کد/خروجی قابل بازتولید، ۴۰٪ تحلیل فارسی

> **نکتهٔ کلیدی:** اگر فقط عدد بنویسی و کد/خروجی نداشته باشی، ۶۰٪ نمره از دست می‌رود. پاسخ عددی بدون شواهد اجرایی پذیرفته نمی‌شود.

## ۳. ترتیب پیشنهادی اجرا

بخش‌های ۵ تا ۱۲ به هم وابسته‌اند؛ ترتیب زیر وابستگی‌ها را رعایت می‌کند:

```
۱–۴    پاسخ‌دهی مفهومی (بدون کد، سریع)
  ↓
۵      آماده‌سازی داده و مهندسی context      ← همهٔ بخش‌های بعدی روی این سوارند
  ↓
۶      ابزارهای محدود و MCP واقعی             ← سه ابزار خواندنی متولد می‌شوند
  ↓
۷      حلقهٔ ابزار و توقف قابل آزمون          ← از سه ابزار بخش ۶ استفاده می‌کند
  ↓
۸      حافظهٔ پایدار + تأیید انسانی (SQLite)  ← روی حلقه سوار می‌شود
  ↓
۹      مسیریابی + معماری چندنقشی              ← روی ۰۳_Requests و ۰۱_HR
  ↓
۱۰     دفاع چندلایه + ده آزمون تهدید          ← روی ابزارها و context بخش‌های قبل
  ↓
۱۱     ارزیابی و مشاهده‌پذیری                 ← روی ۰۷_Evaluation
  ↓
۱۲     انتشار کنترل‌شده و تحویل نهایی          ← همهٔ خروجی‌های بخش‌های ۵ تا ۱۱ را جمع می‌کند
```

## ۵. قاعدهٔ صداقت اجرا

این تکلیف صریحاً بین سه حالت تفکیک می‌کند و این تفکیک مستقیماً نمره دارد:

| مؤلفه          | وضعیت در مرجع              |
| -------------- | -------------------------- |
| SQLite         | **واقعاً اجرا شده**        |
| MCP (stdio)    | **واقعاً اجرا شده**        |
| گراف/LangGraph | **واقعاً اجرا شده**        |
| تصمیم‌گیر مدل  | **fixture** (قطعی، آفلاین) |
| هویت reviewer  | **fixture**                |
| لاگ‌های مقایسه | **fixture**                |
| LLM زنده       | **اجرا نشده**              |
| استقرار عمومی  | **اجرا نشده**              |

اگر در پاسخ «LLM زنده اجرا شد؟» را «بله» بزنی در حالی که fixture بوده، این ادعا مباشرتاً خلاف واقع است و در بخش ۱۲ (`execution_scope`) و زیرسؤال ۶٫۱۱ جریمه دارد. **fixture صریح مجاز و حتی تشویق‌شده است؛ فقط باید نامش را بگویی.**

## ۶. قواعد سخت (نقض = نمرهٔ صفر در آن قلم)

1. تنظیم مدل و آستانه‌ها **فقط** با `train` و `dev`. `test` به‌هیچ‌وجه برای انتخاب پارامتر استفاده نشود.
2. شناسه‌ها (`request_id`، `employee_id`، `attack_id`) و `audit_group` هرگز نباید ویژگی مدل باشند.
3. `test` و `gold` در بسته نیست؛ به‌جای ساختن برچسب جعلی، فیلد معیار خصوصی را دقیقاً بنویس «خصوصی».
4. هیچ رمز، توکن یا API key واقعی در تحویل نباشد.
5. وزن مدل، باینری، دیتاست مشترک و پاسخ مرجع را در ZIP تکرار نکن.
6. `tenant` و نقش مدیر **هرگز** از آرگومان مدل خوانده نشود؛ از principal سمت برنامه بیاید.
7. حافظهٔ دائمی از دستور داخل سند (prompt injection) ساخته نشود.
8. `audit` هرگز برای راحتی خاموش نشود.
9. پاسخ عددی بدون کد و خروجی پذیرفته نیست.
10. گزارش checker خودت مدرک مستقل اجرای درست نیست.

## ۸. تقسیم کار پیشنهادی برای نوت‌بوک

نوت‌بوک قالب (`Student_Template.ipynb`) ۴۴۵ سلول دارد: ۳۰۱ مارک‌داون + ۱۴۴ سلول کد (یکی برای هر زیرسؤال).

برای هر زیرسؤال سه سلول موجود است:

1. `### زیرسؤال N.M` — عنوان
2. سلول کد با `# Write your implementation here.`
3. مارک‌داون با `<div dir="rtl">روش اجرا و تحلیل خود را اینجا بنویسید.</div>`

**قاعده:** در سلول کد، کد انگلیسی و خروجی اجرا؛ در سلول مارک‌داون، تحلیل فارسی راست‌به‌چپ. خروجی سلول کد باید در نوت‌بوک نمایش داده شود (اجرای واقعی، نه نقل خروجی).
