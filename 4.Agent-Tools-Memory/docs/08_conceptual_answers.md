# پاسخ بخش‌های ۱ تا ۴ — تکلیف ۴

مفهومی · ۴۸ زیرسؤال · ۲۴ نمره · مرجع: اسلایدهای جلسهٔ ۴ (`slides_readable.txt`)

> قاعدهٔ نمره: ۶۰٪ گزینهٔ درست + ۴۰٪ دلیل متکی به قید مسئله. در هر پاسخ، دلیل به همان قید مسئله و به اسلاید مرجع اشاره می‌کند.

## بخش ۱ — انتخاب معماری و مرز ایجنت (۶ نمره)

مرجع: اسلاید ۳ (معماری سیستم) و اسلاید ۴ (Workflow vs Agent)

### ۱٫۱ — Workflow قطعی

**دلیل:** مسیر استخراج، اعتبارسنجی و گزارش از پیش تعریف شده و قانون امتیازدهی قطعی است؛ اسلاید ۴ برای همین حالت می‌گوید «یک Prompt یا Workflow ساده کافی است» و «قانون کسب‌وکار قطعی است ← Agent نسازید». گزینهٔ Agent خودمختار و شبکهٔ ده Agent پیچیدگی بی‌توجیه اضافه می‌کنند و «حذف اعتبارسنجی» کنترل را از بین می‌برد.

### ۱٫۲ — Agent با حلقهٔ محدود

**دلیل:** دقیقاً دو شرط «Agent بسازید وقتی...» در اسلاید ۴ برقرار است: «تعداد قدم‌ها از قبل معلوم نیست» و «مسیر به نتیجهٔ هر قدم بستگی دارد». صف بدون منطق تصمیم و prompt ثابت نمی‌توانند مسیر را بر اساس نتیجهٔ ابزار تغییر دهند، و CSS ربطی به معماری تصمیم ندارد.

### ۱٫۳ — L0 ساده

**دلیل:** سامانه یک ورودی می‌گیرد و یک خروجی می‌دهد، بدون ابزار، حافظه، RAG یا حلقه. این تعریف L0 در اسلاید ۴ است («LLM ساده: یک ورودی، یک خروجی»). چون ابزار و حافظه ندارد به L1 نمی‌رسد و چون حلقهٔ تصمیم ندارد L3 نیست.

### ۱٫۴ — Augmented LLM در یک Workflow

**دلیل:** وجود RAG و حافظه سطح L1 (Augmented LLM) می‌سازد، اما چون «ترتیب بازیابی و پاسخ را کد ثابت مشخص می‌کند»، مسیر در سطح L2 قفل شده است؛ اسلاید ۴ برای L2 می‌گوید «مسیر را کد تعیین می‌کند». پس دقیق‌ترین توصیف، ترکیب L1 درون L2 است. صرفِ داشتن RAG، مدل را خودمختار نمی‌کند.

### ۱٫۵ — کد dispatcher پس از اعتبارسنجی

**دلیل:** اسلاید ۵ در حلقهٔ ReAct دستور `result = run_tool(call.name, call.args)  # validated` را نشان می‌دهد؛ و اسلاید ۷ صریح است: «مدل فقط می‌گوید این ابزار را با این پارامترها صدا بزن؛ کد شما اجرا می‌کند». متن پاسخ مدل و نام ابزار در prompt فقط قصد را بیان می‌کنند و اثر واقعی ندارند.

### ۱٫۶ — اثر انگشت عمل تکراری همراه سقف قدم

**دلیل:** اسلاید ۵ «تشخیص حلقهٔ تکراری و Timeout» را از شروط توقف صریح می‌داند. تکرار همان فراخوانی با همان آرگومان یعنی مدل در حلقه افتاده؛ اثر انگشت عمل آن را مستقیم تشخیص می‌دهد و سقف قدم جلوی ادامه را می‌گیرد. افزایش context یا دما علت را رفع نمی‌کند و حذف trace فقط شواهد را از بین می‌برد.

### ۱٫۷ — نتیجه موفق ولی مسیر نامعتبر

**دلیل:** اسلاید ۱۶ می‌گوید هم نتیجه و هم مسیر (Trajectory) سنجیده می‌شود. خواندن پروندهٔ غیرمجاز نقض scope است، حتی اگر پاسخ نهایی درست باشد؛ پس «موفقیت کامل» غلط است و این خطا صرفاً ظاهری نیست.

### ۱٫۸ — کنترل دامنه و اعتبارسنجی خروجی

**دلیل:** اسلاید ۱۴ برای لایهٔ خروجی «Structured Output: خروجی Agent فقط JSON معتبر با فیلدهای مشخص» را الزام می‌کند. توصیهٔ استخدام خودکار خارج از دامنهٔ مجاز است و باید در schema خروجی رد شود، نه با قضاوت متنی. ابزار نوشتن یا بعد بردار بیشتر این شکاف را پر نمی‌کند.

### ۱٫۹ — مقایسهٔ قابل سنجش با baseline تک‌ایجنت

**دلیل:** اسلاید ۱۰ می‌گوید «اول یک Agent خوب بسازید» و چند-Agent فقط وقتی توجیه دارد که «Eval نشان دهد یک Agent از پس کار برنمی‌آید». پس اولین تصمیم، ساختن baseline قابل سنجش است؛ افزودن فوری نقش‌ها یا انتخاب بر اساس تعداد نقش، توجیه تجربی ندارد و حذف baseline مقایسه را ناممکن می‌کند.

### ۱٫۱۰ — کلید idempotency و بازیابی وضعیت

**دلیل:** اسلاید ۳ می‌گوید «کلید Idempotency جلوی اجرای دوباره را می‌گیرد». timeout یعنی وضعیت نامعلوم است؛ فرض شکست قطعی می‌تواند نوشتن دوباره بسازد، و ارسال با کلید تازه همان اثر تکرار را تأیید می‌کند. خاموش‌کردن audit هم نقض جداگانه است.

### ۱٫۱۱ — کنترل پیش از اقدام انجام نشده است

**دلیل:** اسلاید ۵ می‌گوید «سقف هزینه، سقف قدم، Timeout را همیشه صریح بنویسید». اگر سقف هزینه پس از فراخوانی بررسی شود، بودجه بعد از خرج شدن سنجیده می‌شود و کنترل دیگر پیشگیرانه نیست. نام مدل، نمودار و فشردگی context با این نقص ارتباطی ندارند.

### ۱٫۱۲ — شکست زنجیره‌ای

**دلیل:** اسلاید ۱۰ این را صریحاً «Cascading Failure: خطای یکی به همه می‌رسد» می‌نامد. ارسال پاسخ ناقص با قطعیت به همهٔ نقش‌ها خطا را تکثیر می‌کند. cache miss یا context rot این اثر را توضیح نمی‌دهند و «تضمین consensus» با پاسخ ناقص ساخته نمی‌شود.

## بخش ۲ — مهندسی context و قرارداد ابزار (۶ نمره)

مرجع: اسلاید ۵ (آناتومی Agent)، اسلاید ۶ (Context Engineering)، اسلاید ۷ (ابزار و MCP)

### ۲٫۱ — Select

**دلیل:** انتخاب اینکه «کدام سند وارد پنجره شود» راهبرد Select است؛ اسلاید ۶: «Select: فقط مرتبط‌ها را وارد کن». فیلتر tenant و دپارتمان در واقع انتخاب زیرمجموعهٔ مجاز پیش از ورود به پنجره است. Compress و Write دربارهٔ حجم و محل نگهداری‌اند، نه انتخاب.

### ۲٫۲ — Write

**دلیل:** اسلاید ۶: «Write: بیرون از پنجره ذخیره کن: Scratchpad، فایل یادداشت، State». انتقال نتیجهٔ حجیم به فایل بیرونی و نگه‌داشتن فقط شناسه و خلاصه، دقیقاً همین است. Voting و افزایش دما بیربط‌اند و Select مربوط به ورود اطلاعات است نه خروج آن.

### ۲٫۳ — Compress

**دلیل:** اسلاید ۶: «Compress: خلاصه کردن تاریخچه، حذف Tool Resultهای قدیمی، نگه داشتن فقط فیلدهای لازم از JSON». حفظ عدم قطعیت هم شرط کیفیت فشرده‌سازی است. این کار تزریق را رفع نمی‌کند (گزینهٔ A ادعای زیادی است) و شواهد را هم کاملاً حذف نمی‌کند.

### ۲٫۴ — Isolate

**دلیل:** اسلاید ۶: «Isolate: زیر-Agent با Context تمیز و جدا؛ فقط نتیجه خلاصه برمی‌گردد». خواندن رزومه در context جدا و برگرداندن فقط ادعاهای ساختاریافته همان الگو است. اشتراک کامل history (B) عکس این است و افزایش دسترسی (D) نقض امنیت است.

### ۲٫۵ — ۱۰۰۰

**دلیل:** ظرفیت ورودی = پنجره منهای ذخیرهٔ پاسخ. ۱۲۰۰ − ۲۰۰ = ۱۰۰۰ واحد. گزینهٔ ۱۲۰۰ کل پنجره است و ذخیرهٔ پاسخ را نادیده می‌گیرد؛ ۱۴۰۰ از پنجره بیشتر است و ۲۰۰ فقط ذخیرهٔ پاسخ است.

### ۲٫۶ — تابع محدود با schema و enum مشخص

**دلیل:** اسلاید ۷: «ورودی محدود: enum و اعتبارسنجی؛ نه SQL آزاد». ابزار با SQL آزاد سطح حمله را به کل پایگاه باز می‌کند. نام طولانی‌تر یا عبارت «لطفاً امن باش» در prompt هیچ قید اجرایی نمی‌سازد و رهاکردن ورودی بدترین حالت است.

### ۲٫۷ — اختلاط ورودی مدل با هویت قابل اعتماد

**دلیل:** این نقص، همان قاعدهٔ «tenant فقط از principal» را می‌شکند: اگر سرور مقداری را که مدل در `arguments` فرستاده هویت معتبر بگیرد، مدل می‌تواند آن را جعل کند. گزینه‌های tokenizer، compression و top_k هیچ ارتباطی با مرز هویت ندارند.

### ۲٫۸ — Tools و Resources و Prompts

**دلیل:** اسلاید ۷ صریح است: «هر Server سه چیز ارائه می‌دهد: Tools، Resources، Prompts». گزینه‌های دیگر یا مفاهیم آموزش مدل‌اند (train/dev/test) یا زیرساخت (GPU، HTTP GET) و ربطی به قابلیت‌های MCP ندارند.

### ۲٫۹ — پیام‌های پروتکل

**دلیل:** در transport stdio، `stdout` کانال JSON-RPC است و باید فقط برای پیام‌های پروتکل رزرو شود. هر `print` اضافی جریان را می‌شکند؛ به همین دلیل لاگ‌ها باید به `stderr` یا فایل بروند. نمایش رمز اتصال هم نقض امنیتی است.

### ۲٫۱۰ — پیشنهاد ابزار توسط مدل باید در برنامه اجرا و اعتبارسنجی شود

**دلیل:** اسلاید ۷: «مدل فقط می‌گوید این ابزار را با این پارامترها صدا بزن؛ کد شما اجرا می‌کند». پس tool call خودکار موفق نیست، JSON مجوز مدیر نمی‌سازد، و schema جای RBAC را نمی‌گیرد؛ schema فقط شکل داده را کنترل می‌کند.

### ۲٫۱۱ — MCP قرارداد دسترسی به قابلیت‌هاست؛ ارتباط agentها مسئلهٔ جداگانه دارد

**دلیل:** اسلاید ۷ دو محور را جدا می‌کند: MCP برای «مدل ↔ ابزار» است و A2A («پروتکل گفتگوی Agentها با هم») برای «agent ↔ agent». پس یک JSON داخلی، پیاده‌سازی کامل A2A نیست و MCP هم لزوماً ابزار نوشتن نیست.

### ۲٫۱۲ — دادهٔ نامطمئن بدون اختیار تغییر سیاست

**دلیل:** اسلاید ۱۳ و ۱۴: محتوای برگشتی از ابزار یا سند، «داده» است نه «دستور». متن داخل سند بازیابی‌شده نمی‌تواند سیاست را عوض کند یا مجوز بسازد؛ اگر چنین اختیاری داشت، همان تزریق غیرمستقیم (Indirect injection) رخ داده است.

## بخش ۳ — حافظه و الگوهای گردش کار (۶ نمره)

مرجع: اسلاید ۸ (State و Memory) و اسلاید ۹ (Workflow Patterns)

### ۳٫۱ — Semantic بلندمدت

**دلیل:** اسلاید ۸: «Semantic: حقایق» — اطلاعات پایدار دربارهٔ فرد که بین نشست‌ها معنا دارد. working memory با پایان session پاک می‌شود و checkpoint فقط وضعیت اجرا را نگه می‌دارد، نه محتوای دانشی.

### ۳٫۲ — Episodic

**دلیل:** اسلاید ۸: «Episodic: تجربه‌ها (جلسهٔ هفتهٔ پیش با علی)». یادداشت اینکه در بررسی قبلی چه گذشت، ثبت تجربه است نه حقیقت پایدار و نه روش. Prompt template و Tool schema هم اصلاً حافظه نیستند.

### ۳٫۳ — Procedural

**دلیل:** اسلاید ۸: «Procedural: روش‌ها (Prompt و قواعد بهبودیافته)». نسخهٔ تأییدشدهٔ روش بازبینی یک رویه است. Episodic تجربهٔ یک رخداد است و session history فقط تاریخچهٔ گفتگو.

### ۳٫۴ — Working memory

**دلیل:** اسلاید ۸ حافظهٔ کوتاه‌مدت را «تاریخچهٔ گفتگو، Tool Resultهای همین وظیفه، Scratchpad» می‌داند و می‌گوید «با پایان Session پاک می‌شود». Semantic دائمی و مجوز ثبت پروفایل تعریف‌های دیگری دارند.

### ۳٫۵ — checkpoint پایدار و شناسهٔ وظیفه

**دلیل:** اسلاید ۸: «وضعیت هر قدم ذخیره شود تا بعد از خطا یا تأیید انسان، از همان جا ادامه دهد (State Machine / Graph)». متغیر Python در RAM با crash از بین می‌رود و prompt بلندتر وضعیت را بازیابی نمی‌کند.

### ۳٫۶ — Prompt Chaining

**دلیل:** اسلاید ۹: «Prompt Chaining: خروجی هر قدم، ورودی بعدی؛ با Gate بین قدم‌ها». عبور از schema gate پیش از رفتن به گزارش دقیقاً همان gate بین قدم‌هاست. Voting بدون gate و handoff نامحدود کنترل ندارند.

### ۳٫۷ — Routing

**دلیل:** اسلاید ۹: «Routing: دسته‌بندی ورودی و ارسال به مسیر تخصصی». ارجاع درخواست مالی و بازاریابی به ابزار مربوط، همان طبقه‌بندی و مسیردهی است. Compression، Rollback و Parallelization کارهای دیگری می‌کنند.

### ۳٫۸ — Parallelization با sectioning

**دلیل:** اسلاید ۹: «چند زیروظیفه هم‌زمان (Sectioning)». دو ارزیابی مستقل که هم‌زمان اجرا و سپس تجمیع می‌شوند همین الگو را می‌سازند. Voting رأی‌گیری روی یک پرسش است و زنجیرهٔ ترتیبی موازی‌سازی را از دست می‌دهد.

### ۳٫۹ — Orchestrator–Workers

**دلیل:** اسلاید ۹: «Orchestrator–Workers: Agent اصلی وظایف را پویا تقسیم و نتایج را ترکیب می‌کند». انتخاب پویای تعداد متخصص بر اساس ورودی، همان تصمیم هماهنگ‌کننده است. زنجیرهٔ ثابت و cache این انعطاف را ندارند.

### ۳٫۱۰ — Evaluator–Optimizer

**دلیل:** اسلاید ۹: «Evaluator–Optimizer: یکی تولید می‌کند، دیگری نقد؛ تا رسیدن به معیار». سقف دو بار اصلاح همان شرط توقف است. ذخیرهٔ بدون بازبینی حلقهٔ بهبود ندارد و handoff بدون مقصد الگو نیست.

### ۳٫۱۱ — نقش‌ها به context و مجوزهای متفاوت نیاز دارند

**دلیل:** اسلاید ۱۰ دو توجیه اصلی چند-Agent را می‌آورد: «Context جدا برای هر نقش» و «نقش‌ها دسترسی متفاوت لازم دارند». اگر همه یک history و یک دسترسی داشته باشند (B)، تفکیک نقش ارزشی ندارد؛ نام جذاب‌تر و نبود baseline هم توجیه نیستند.

### ۳٫۱۲ — بازپخش یا تحویل به نقش نامناسب

**دلیل:** اسلاید ۱۰: «پیام بین Agentها باید احراز و ثبت شود». امضا فقط اصالت را می‌گوید؛ بدون بررسی مقصد و انقضا، پیام معتبر می‌تواند بازپخش شود یا به نقش نادرست برسد. استقلال و trace هم با این نقص تأمین نمی‌شوند.

## بخش ۴ — اختیار انسانی و ارزیابی استقرار (۶ نمره)

مرجع: اسلاید ۱۱ (سطوح خودمختاری)، ۱۲ (سطوح استقرار)، ۱۳ (تهدیدها)، ۱۴ (دفاع چندلایه)، ۱۶ (ارزیابی)، ۱۷ (ملاحظات استقرار)

### ۴٫۱ — L1 Operator

**دلیل:** اسلاید ۱۱: «L1 Operator · اپراتور: کاربر هدایت می‌کند؛ Agent فقط وقتی خواسته شود کمک می‌کند». چون کاربر هر اقدام را خودش هدایت می‌کند و Agent فقط پیشنهاد می‌دهد، L1 است. L3 Consultant آن است که Agent هدایت کند و از کاربر نظر بپرسد.

### ۴٫۲ — L4 Approver

**دلیل:** اسلاید ۱۱: «L4 Approver · تأییدکننده: Agent مستقل کار می‌کند؛ کاربر فقط تصمیم‌های پرریسک را تأیید می‌کند». ساخت پیش‌نویس مستقل و تأیید کارشناس فقط برای ثبت حساس، همین الگو است. L1 آن نیست چون Agent مستقل کار می‌کند.

### ۴٫۳ — Shadow

**دلیل:** اسلاید ۱۲: «Shadow: موازی با انسان، مقایسهٔ نتایج» و «Shadow Mode: بدون اثر واقعی». اجرای کنار کارشناس بدون اثر واقعی، تعریف shadow است. Canary با نوشتن واقعی روی درصدی از ترافیک کار می‌کند، نه بدون اثر.

### ۴٫۴ — Canary

**دلیل:** اسلاید ۱۲: «Canary: ۵٪ ترافیک، سپس بیشتر» همراه با «Feature Flag: خاموش کردن فوری» و «Pass Criteria». واحد تست و افزایش context هیچ‌کدام انتشار تدریجی با قابلیت برگشت نیستند.

### ۴٫۵ — Indirect

**دلیل:** اسلاید ۱۳: «Indirect: دستور در داده پنهان است: ایمیل، متن پیام صوتی، وب، سند RAG، خروجی ابزار». متن مخرب داخل رزومه که وارد context می‌شود، داده است نه ورودی مستقیم کاربر. پس Direct و SQL transaction و Timeout رد می‌شوند.

### ۴٫۶ — قطع یا محدودکردن حداقل یک ضلع این ترکیب

**دلیل:** اسلاید ۱۳ «Lethal Trifecta» را تعریف می‌کند: دسترسی به دادهٔ خصوصی + خواندن محتوای غیرقابل اعتماد + توانایی ارتباط بیرونی. با یک تزریق، داده نشت می‌کند، پس باید حداقل یک ضلع را قطع کرد. قوی‌کردن جملهٔ system کافی نیست چون هیچ روشی تزریق را ۱۰۰٪ حل نمی‌کند.

### ۴٫۷ — Automation bias

**دلیل:** اسلاید ۱۱: «Automation Bias: انسانی که صد بار تأیید زده، دیگر نمی‌خواند». صد تأیید بدون خواندن یعنی مکانیزم تأیید عملاً از کار افتاده. این خطر، کاهش هزینه یا استقلال reviewer نیست و تزریق را هم رفع نمی‌کند.

### ۴٫۸ — Memory poisoning

**دلیل:** اسلاید ۸: «Memory Poisoning: اگر Agent از متن ورودی چیزی را در حافظهٔ بلندمدت بنویسد، مهاجم می‌تواند دستوری بکارد که هفته‌ها بعد اجرا شود». ذخیرهٔ دستور مخرب و قانون‌شدن آن در نشست بعد، همین حمله است.

### ۴٫۹ — ابزار و آرگومان و ترتیب مجاز

**دلیل:** اسلاید ۱۶: «Trajectory: ابزار درست، با پارامتر درست، به ترتیب معقول؟». ارزیابی مسیر یعنی همین، مستقل از زیبایی پاسخ یا تعداد پارامتر مدل. زمان کل هم معیار مسیر نیست بلکه معیار کارایی است.

### ۴٫۱۰ — بیشینهٔ پایان منهای کمینهٔ شروع

**دلیل:** spanها موازی‌اند، پس جمع همهٔ مدت‌ها زمان دیواری نیست و عدد را متورم می‌کند. زمان دیواری هر run برابر است با دیرترین پایان منهای زودترین شروع. تعداد span و کمترین worker هیچ‌کدام زمان دیواری نمی‌دهند.

### ۴٫۱۱ — نمونه برای ادعای برابری کافی نیست

**دلیل:** سه نمونه پایهٔ آماری برای ادعای برابری ندارد؛ نتیجه باید تعریف‌نشده تلقی شود نه «برابری اثبات‌شده». حذف گروه داده را از بین می‌برد و واردکردن gold به ورودی مدل هم نشت برچسب است.

### ۴٫۱۲ — مالک و هدف و ابزار و سطح اختیار و معیار ارجاع و بودجه

**دلیل:** اسلاید ۱۷: «یک Agent Card برای هر Agent بنویسید: هدف، مالک، ابزارها و دسترسی‌ها، سطح خودمختاری، شرایط ارجاع به انسان، معیارهای Eval، هزینهٔ مجاز». لوگو، تاریخ ساخت و نام مدل هیچ‌کدام این مسئولیت‌پذیری را نمی‌سازند.
