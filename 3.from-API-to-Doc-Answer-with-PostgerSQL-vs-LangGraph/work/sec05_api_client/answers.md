## زیرسؤال ۵٫۱

**فیلدهای خواسته‌شده و پاسخ دقیق:**

| فیلد کارت            | پاسخ       |
| -------------------- | ---------- |
| تعداد درخواست        | **2400**   |
| شناسهٔ تکراری        | **0**      |
| نرخ خطا بین صفر و یک | **0.5863** |

**چرا این کار:** پیش از هر تحلیل، خود فایل لاگ را ممیزی کردم که چند ردیف دارد، آیا `request_id` یکتاست و چه سهمی از درخواست‌ها خطاست.

**خروجی اجرا:**

```
rows: 2400
unique request_id: 2400
duplicate request_id: 0
error rate (status>=400): 0.5863
synthetic flag values: ['True']
```

**تحلیل:** نرخ خطا از `status >= 400` محاسبه شد، نه از حدس: `1407 / 2400 = 0.58625` که به چهار رقم `0.5863` می‌شود. تعریف «خطا» صریح است و `2xx` موفق حساب شده، پس `3xx` هم در این شمارش خطا نیست (در این داده اصلاً وجود ندارد).

**مصنوعی‌بودن داده:** ستون `synthetic` برای همهٔ ۲۴۰۰ ردیف `True` است و فایل `provider_config.json` هم `pricing_is_fictional: true` دارد. این ۵۸٫۶۳٪ نرخ خطای یک سرویس واقعی نیست؛ یک مجموعهٔ آموزشی است که عمداً تراکم خطا دارد تا مسیرهای retry و envelope آزموده شوند. هر تفسیری دربارهٔ «کیفیت ارائه‌دهنده» از دل این عدد، ادعای بیش از شاهد است.

## زیرسؤال ۵٫۸

**فیلدهای خواسته‌شده و پاسخ دقیق:**

| فیلد کارت                       | پاسخ            |
| ------------------------------- | --------------- |
| تعداد تلاش                      | **3**           |
| جمع زمان انتظار برنامه‌ریزی‌شده | **1.5** (ثانیه) |

**چرا این کار:** سقف تلاش باید هم تعداد و هم زمان را محدود کند، ولی این دو یکی نیستند.

**خروجی اجرا:** سناریوی خطای مداوم `[503, 503, 503, 503]` با `max_attempts=3`:

```
attempts used: 3
planned waits: [0.5, 1.0] sum: 1.5
stopped reason: attempts_exhausted
with inner deadline 1.2s -> waits: [0.5] reason: deadline_would_be_exceeded
```

سه تلاش انجام شد، دو انتظار برنامه‌ریزی شد (`0.5` و `1.0`، یعنی backoff نمایی با پایهٔ ۰٫۵ و سقف ۵)، و جمع آن‌ها **۱٫۵** ثانیه است. تلاش چهارم هرگز انجام نشد چون سقف تلاش سه است. وقتی بودجهٔ داخلی ۱٫۲ ثانیه گذاشتم، فقط یک انتظار `0.5` ثبت شد و حلقه پیش از انتظار دوم متوقف شد.

**تحلیل چرا سقف تلاش، deadline را تضمین نمی‌کند:** سقف تلاش فقط **تعداد** را می‌بندد و دربارهٔ **زمان** هیچ نمی‌گوید، چون هر تلاش علاوه بر انتظار backoff، زمان اجرای خود درخواست (اتصال + خواندن پاسخ) را هم مصرف می‌کند. سه مؤلفه جدا هستند:

| مؤلفه                        | چه چیزی را می‌بندد       | در این آزمون           |
| ---------------------------- | ------------------------ | ---------------------- |
| `max_attempts = 3`           | تعداد تلاش               | ۳                      |
| `backoff` با سقف ۵ ثانیه     | فاصلهٔ بین تلاش‌ها       | ۰٫۵ و ۱٫۰              |
| `inner_deadline` / بودجهٔ کل | کل زمان از شروع تا پایان | ۱٫۲ ثانیه → توقف زودتر |

نمونهٔ عددی برای اثبات: اگر سقف تلاش ۳۰۰ و سقف هر backoff ۵ ثانیه باشد، فقط انتظارها می‌توانند ۱۵۰۰ ثانیه شوند، بدون احتساب زمان خودِ درخواست‌ها. پس سقف تلاش بدون بودجهٔ زمانی می‌تواند تا دقیقه‌ها طول بکشد و deadline سرویس را نقض کند. به همین دلیل دو کنترل جدا لازم است: یکی تعداد را می‌بندد، دیگری زمان را.

| نوع             | معنا                                         | در این آزمون |
| --------------- | -------------------------------------------- | ------------ |
| connect timeout | TCP/TLS برقرار نشد؛ هیچ بایتی از پاسخ نرسید  | ۰٫۵ ثانیه    |
| read timeout    | اتصال برقرار شد ولی پاسخ در زمان مقرر نرسید  | ۰٫۳ ثانیه    |
| بودجهٔ کل       | جمع همهٔ تلاش‌ها و انتظارها از شروع تا پایان | ۳٫۰ ثانیه    |

دلیل اینکه این سه را نمی‌توان یکی گرفت: connect timeout دربارهٔ دسترسی به میزبان است، read timeout دربارهٔ سرعت پاسخ‌دهی پس از اتصال، و بودجهٔ کل سقف مصرف کاربر است. یک درخواست می‌تواند اتصالش سریع باشد ولی خواندنش کند شود؛ برعکسش هم ممکن است.

**چرا هیچ خطایی موفقیت معرفی نشد:** استثنا به `TimeoutBudgetError` تبدیل شد و در مسیر فراخوانی بالا رفت. هیچ `try/except` ای پاسخ خالی یا `None` برنگرداند، و بودجهٔ از پیش منقضی **قبل از ارسال** رد شد. اگر ReadTimeout را «پاسخ خالی» حساب می‌کردیم، یک خروجی نامعتبر جای موفقیت می‌نشست — همان قید ۲٫۱۲ در سطح کلاینت.

## زیرسؤال ۵٫۱۰

**فیلد خواسته‌شده و پاسخ دقیق:**

| فیلد کارت                 | پاسخ         |
| ------------------------- | ------------ |
| کل هزینهٔ فرضی بر حسب USD | **0.833118** |

**فرض قیمت، صریح:** واحد فایل «per million tokens» است، ارز `USD`، و `pricing_is_fictional: true`. نرخ‌ها:

| ارائه‌دهنده | ورودی (USD / 1M tokens) | خروجی (USD / 1M tokens) |
| ----------- | ----------------------- | ----------------------- |
| provider_a  | 0.4                     | 1.2                     |
| provider_b  | 0.1                     | 0.4                     |

**چرا این کار:** هزینهٔ هر درخواست = `(input_tokens / 1e6) × نرخ ورودی + (output_tokens / 1e6) × نرخ خروجی`. سپس جمع هر provider و جمع کل.

**خروجی اجرا:**

| ارائه‌دهنده | درخواست | توکن ورودی | توکن خروجی | هزینه (USD)  |
| ----------- | ------- | ---------- | ---------- | ------------ |
| provider_a  | 1200    | 923827     | 229752     | **0.645233** |
| provider_b  | 1200    | 937950     | 235225     | **0.187885** |
| **جمع**     | 2400    | —          | —          | **0.833118** |

**مقایسه و تحلیل:** provider_b با وجود **توکن بیشتر** (۹۳۷۹۵۰ در برابر ۹۲۳۸۲۷ ورودی و ۲۳۵۲۲۵ در برابر ۲۲۹۷۵۲ خروجی) حدود **۳٫۴ برابر ارزان‌تر** است، چون نرخ‌هایش یک‌چهارم است. یعنی اگر فقط تعداد توکن را نگاه کنیم تصمیم اشتباه می‌گیریم؛ هزینه تابع نرخ × حجم است و حجم تقریباً برابر. سهم provider_a از کل هزینه **۷۷٫۴٪** است در حالی که سهمش از توکن‌ها ۴۹٫۶٪ است — همین نشان می‌دهد تفاوت از نرخ می‌آید نه از بار.

**دو محدودیت که باید در گزارش بیاید:**

| محدودیت                                                      | چرا مهم است                                                                                                                                                                                                                   |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| قیمت‌ها فرضی‌اند (`pricing_is_fictional: true`)              | این اعداد قیمت واقعی هیچ vendor ای نیستند و نباید نقل شوند                                                                                                                                                                    |
| این جمع، هزینهٔ **همهٔ** ۲۴۰۰ ردیف است، شامل ردیف‌های خطادار | هزینهٔ ردیف‌های ناموفق فقط اگر ارائه‌دهنده توکن مصرف کرده باشد واقعی است؛ برای مقایسهٔ «هزینهٔ پاسخ‌های موفق» جمع ردیف‌های `status == 200` برابر است با **0.342138** USD (۹۹۳ ردیف: provider_a ۰٫۲۶۶۳۹ + provider_b ۰٫۰۷۵۷۴۸) |

بیشترین هزینهٔ یک درخواست: `REQ-02258` با **0.000976** USD. نمونهٔ محاسبه: `REQ-00000` با ۵۰۱ ورودی و ۲۴۸ خروجی روی provider_a = ۰٫۰۰۰۴۹۸ دلار.

## زیرسؤال ۵٫۱۲

**فیلدهای خواسته‌شده و پاسخ دقیق:**

| فیلد کارت            | پاسخ          |
| -------------------- | ------------- |
| تعداد آزمون قالب خطا | **2**         |
| وضعیت‌های بازگشتی    | **401 و 422** |

**چرا این کار:** خطا باید شکل ثابت داشته باشد تا کلاینت بر اساس `code` تصمیم بگیرد، نه با پارس کردن متن.

**خروجی اجرا:**

```
401 missing identity     -> 401 keys=['code', 'correlation_id', 'message'] shaped=True
    {'code': 'unauthenticated', 'message': 'Missing X-User-ID header.', 'correlation_id': 'CORR-90c7db556ef0'}
422 top_k out of range   -> 422 keys=['code', 'correlation_id', 'message'] shaped=True
    {'code': 'validation_error', 'message': 'top_k: Input should be less than or equal to 10', 'correlation_id': 'CORR-1fc8adb123a0'}
envelope checks: 2 | all shaped: True | statuses: [401, 422]
```

**تحلیل:** هر دو پاسخ دقیقاً سه کلید دارند و هیچ کلید اضافه یا فیلد خصوصی ندارند. سه دلیل که این قالب مهم است:

| ویژگی                                                      | فایده                                                           |
| ---------------------------------------------------------- | --------------------------------------------------------------- |
| `code` ماشین‌خوان (`unauthenticated` / `validation_error`) | کلاینت می‌تواند تصمیم بگیرد بدون parse کردن متن انگلیسی         |
| `message` کوتاه و بدون دادهٔ کاربر                         | خطا نباید متن خصوصی پرونده را در پاسخ تکرار کند (قید ۵٫۵ و ۳٫۹) |
| `correlation_id`                                           | پاسخ خطا را به trace همان درخواست وصل می‌کند                    |

نکتهٔ قرارداد: `RequestValidationError` در FastAPI پیش‌فرض بدنهٔ `{"detail": [...]}` می‌دهد؛ هندلر ما آن را به همان envelope تبدیل می‌کند تا ۴۲۲ با ۴۰۱ هم‌شکل باشد. بدون این هندلر، کلاینت برای هر خانوادهٔ خطا یک parser جدا لازم داشت. خطای ۵۰۰ هم از همین مسیر می‌گذرد و `correlation_id` را حفظ می‌کند.

## محدودیت‌ها و مرز اجرا

- **واقعاً اجراشده:** ممیزی ۲۴۰۰ لاگ واقعی روی دیسک، محاسبهٔ backoff و هزینه، FastAPI `TestClient` روی یک اپ محلی، `MockTransport` برای قرارداد ارائه‌دهنده. (cosine مربوط به بخش ۸ است و در این بخش محاسبه نشده.)
