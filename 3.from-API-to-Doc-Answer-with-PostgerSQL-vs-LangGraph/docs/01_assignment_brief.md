## قالب پاسخ — سه سلول برای هر زیرسؤال

برای هر زیرسؤال، به همین ترتیب:

1. **Markdown** با عنوان `زیرسؤال ۵٫۳` و صورت سؤال (اعداد با `٫` فارسی).
2. **Code** انگلیسی و قابل اجرا که خروجی را چاپ کند.
3. **Markdown فارسی راست‌به‌چپ** با تحلیل: چه کردی، عدد چه می‌گوید، محدودیت چیست.

تصحیح‌کننده با همین عنوان‌ها سلول‌ها را پیدا می‌کند؛ بدون عنوان، بخش عملی آن سؤال کم‌نمره می‌شود. نوت‌بوک باید با Restart Kernel و Run All اجرا شده باشد تا خروجی‌ها ذخیره شوند.

## نحوهٔ تصحیح

| نوع سؤال | وزن |
|---|---|
| مفهومی | ۶۰٪ گزینه + ۴۰٪ دلیل |
| عملی | ۶۰٪ اجرا و نتیجهٔ بازتولیدپذیر + ۴۰٪ تحلیل متناسب با شواهد |

- گزینه‌ها، فایل‌های پیش‌بینی و بخش اجرایی سؤال‌های دیتابیس با **کد** سنجیده می‌شوند.
- دلیل‌ها و تحلیل‌ها را ایجنت می‌خواند و با نوت‌بوک تطبیق می‌دهد.
- فایل دیتابیس یک بررسی خودکار می‌خواند (جدول‌ها، کلید خارجی، تعداد داده، بردار ۳۸۴بعدی، rollback) — همان `grading/check_day3_db.py`.
- **هیچ چیزی اجرا نمی‌شود**: نوت‌بوک فقط خوانده می‌شود و دیتابیس فقط باز و بررسی می‌شود.
- زمان و hash با مرجع تطبیق سخت داده نمی‌شوند (به دستگاه وابسته‌اند).
- استدلال درست دربارهٔ شکست مدل یا محدودیت داده نمره دارد؛ متریک بالا به‌تنهایی هدف نیست.

## مرز اجرا — چه چیزی واقعی است و چه چیزی نیست

| واقعی | fixture (مصنوعی) | اجرا‌نشده |
|---|---|---|
| ۲۴ سند PEP با hash و منشأ | ۲۰ کاربر، ۱۲۰ پرونده، ۲۴۰۰ لاگ | ورود زندهٔ Google / OIDC |
| مدل embedding محلی (`all-MiniLM-L6-v2`) | توکن هویت، پاسخ‌های ارائه‌دهنده | فراخوانی LLM پولی |
| محاسبهٔ cosine و TF-IDF | ۳۰ حمله، ۴۸۰۰ رویداد | PostgreSQL و Docker |
| SQLite واقعی | قیمت‌های ارائه‌دهنده | استقرار اینترنتی |

## قواعد صریح تکلیف

1. تنظیمات را فقط با **train/dev** انتخاب کن و پیش از ساختن فایل‌های test **قفل** کن.
2. هیچ **رمز، API key یا توکن واقعی** در نوت‌بوک و فایل دیتابیس نگذار.
3. پاسخ دادن به هیچ سؤالی اجباری نیست؛ سؤال بی‌پاسخ نمره‌ای نمی‌گیرد (اما نمرهٔ آن هم نمی‌آید).
4. عددهای سایت باید با خروجی نوت‌بوک یکی باشند.
5. بیش از شواهد ادعا نکن: «واقعاً اجراشده»، «fixture»، «اجرا‌نشده» را جدا بنویس.
