# پاسخ‌های بخش ۳ — انتخاب موتور و زیرساخت

## 3.1

**سؤال:** کنترل CLI روی GGUF و CPU بدون GPU اختصاصی نیاز است. نقطهٔ شروع سازگار چیست؟

**گزینهٔ منتخب:** `1` — llama.cpp با build مناسب سیستم

**دلیل:** llama.cpp عمداً برای اجرای GGUF روی CPU طراحی شده و CLI و سرور HTTP داخلی دارد. تکلیف هم دقیقاً همین را الزام کرده: `download_resources.py` نسخهٔ `llama-b11696-bin-win-cpu-x64.zip` را دریافت می‌کند و `runtime_config.json` باید `engine="llama.cpp"` و `backend="CPU"` داشته باشد. گزینه ۰ (درایور CUDA روی هر CPU) دسته‌بندی غلط است — CUDA نیازمند GPU NVIDIA است؛ گزینه ۲ (MLX) مخصوص Apple Silicon است نه عمومی؛ گزینه ۳ (vLLM) به‌طور معمول به GPU و به فرمت‌های دیگر نیاز دارد و در این تکلیف اجرا نشده است.

## 3.2

**سؤال:** کاربر غیرفنی می‌خواهد مدل‌ها را با رابط گرافیکی آزمایش کند. کدام گزینه با قید رابط سازگارتر است؟

**گزینهٔ منتخب:** `3` — LM Studio با backend مناسب

**دلیل:** قید اصلی «رابط گرافیکی برای کاربر غیرفنی» است، نه کنترل برنامه‌نویسانه. LM Studio یک GUI کامل برای بارگذاری GGUF، انتخاب مدل، و گفت‌وگو می‌دهد و در پشت صحنه از موتورهای سازگار استفاده می‌کند. گزینه ۰ (اجبار به ساخت CUDA از سورس) قید مهارت را نقض می‌کند؛ گزینه ۱ (فقط ویرایش سورس C++) همان مشکل را دارد؛ گزینه ۲ (فقط API پولی بیرونی) با «اجرای محلی» در تناقض است و در تکلیف هم اجرای ابری ممنوع است.

## 3.3

**سؤال:** روی Apple Silicon برای استفاده از حافظهٔ unified چه گزینه‌ای تخصصی‌تر است؟

**گزینهٔ منتخب:** `2` — MLX-LM با مدل سازگار

**دلیل:** MLX چارچوب اپل برای Apple Silicon است و مستقیماً روی حافظهٔ unified کار می‌کند (بدون کپی صریح به VRAM جدا). MLX-LM لایهٔ مدل‌های زبانی آن است. نکتهٔ مهم: مدل باید **سازگار** باشد — فرمت MLX با GGUF یکی نیست. تکلیف همین را در بخش ۳.۳ می‌پرسد و در `hardware_inventory.csv` هم `H03` برچسب `Metal` دارد. گزینه ۰ (FPGA بدون toolchain) بی‌ربط؛ گزینه ۱ (فرض یکسان بودن هر GGUF با فرمت MLX) صریحاً نادرست است — نیاز به تبدیل دارد؛ گزینه ۳ (باینری CUDA ویندوز) روی macOS اجرا نمی‌شود.

## 3.4

**سؤال:** برای ده‌ها درخواست هم‌زمان روی GPU سازگار، کدام ویژگی موتور اولویت دارد؟

**گزینهٔ منتخب:** `1` — continuous batching و مدیریت KV همراه سنجش SLO

**دلیل:** با ده‌ها درخواست هم‌زمان، گلوگاه به بهره‌وری batch و مدیریت حافظهٔ KV منتقل می‌شود. continuous batching اجازه می‌دهد درخواست تکمیل‌شده از batch خارج و درخواست جدید وارد شود بدون انتظار برای کندترین عضو (سؤال ۳.۵ همین را می‌پرسد). مدیریت KV (PagedAttention) از پر شدن حافظه و swap جلوگیری می‌کند. و بدون سنجش SLO، این قابلیت‌ها فقط ادعا هستند. گزینه ۰ (GUI) ربطی به بار هم‌زمان ندارد؛ گزینه ۲ (دمای sampling) کیفیت را تغییر می‌دهد نه throughput؛ گزینه ۳ (نام طولانی‌تر مدل) بی‌معنی است.

## 3.5

**سؤال:** در continuous batching یک درخواست تمام می‌شود. رفتار مورد انتظار چیست؟

**گزینهٔ منتخب:** `2` — ورود درخواست جدید بدون انتظار برای پایان کل batch

**دلیل:** این تعریف دقیق continuous batching است (در برابر static batching که کل batch را قفل می‌کند). به‌محض آزاد شدن یک slot، درخواست در صف وارد می‌شود و نرخ استفاده از سخت‌افزار بالا می‌ماند. تکلیف در بخش ۱۰ همین را با شبیه‌ساز می‌سنجد: `P95 static` در برابر `P95 continuous` و نسبت `makespan سری/continuous`. گزینه ۰ (پاک‌کردن وزن مدل برای هر توکن) فاجعهٔ کارایی است؛ گزینه ۱ (توقف همه تا پایان طولانی‌ترین پاسخ) همان رفتار static است که می‌خواهیم از آن اجتناب کنیم؛ گزینه ۳ (تضمین سرعت یکسان) نادرست — تأخیر هر درخواست به طول خودش بستگی دارد.

## 3.6

**سؤال:** چند درخواست prefix ثابت مشترک دارند. تکنیک مرتبط در SGLang چیست؟

**گزینهٔ منتخب:** `2` — RadixAttention و بازاستفادهٔ prefix سازگار

**دلیل:** RadixAttention در SGLang ساختار prefix مشترک را در یک درخت رادیکس نگه می‌دارد و KV محاسبه‌شده برای prefix مشترک را بازاستفاده می‌کند؛ نتیجهٔ آن صرفه‌جویی در prefill و کاهش TTFT برای درخواست‌های بعدی است. تکلیف در بخش ۱۰.۸ و ۱۰.۹ همین ایده را در سطح شبیه‌سازی می‌سنجد: کلید cache از `tenant+revision+prefix` و شمارش hit و «نسبت صرفه‌جویی prompt». گزینه ۰ (افزایش پارامتر کل) بی‌ربط و مضر؛ گزینه ۱ (کاهش فایل CSV) بی‌ربط؛ گزینه ۳ (تعویض مجوز فایل) بی‌ربط.

## 3.7

**سؤال:** با تغییر base_url به سرور محلی کد اتصال کار می‌کند. کدام مورد هنوز باید آزموده شود؟

**گزینهٔ منتخب:** `3` — chat template و schema و ابزار و معنای پاسخ

**دلیل:** سازگاری URL فقط می‌گوید درخواست HTTP به مقصد رسید. آنچه واقعاً تعیین می‌کند سرویس کار می‌کند یا نه این‌ها هستند: قالب chat (که اگر متفاوت باشد مدل دستور را نمی‌فهمد)، پشتیبانی schema (structured output که بخش ۸.۷ و ۸.۸ به آن وابسته‌اند)، پشتیبانی function calling (که بخش ۱۲ به آن وابسته است)، و معنای فیلدهای پاسخ (مثلاً `finish_reason` و `usage` ممکن است بین موتورها متفاوت باشند). تکلیف در ۸.۲ هم می‌پرسد چرا قالب Base و Instruct را نباید یکسان فرض کرد. گزینه ۰ (رنگ آیکون) بی‌ربط؛ گزینه ۱ (همسانی قطعی تمام قابلیت‌ها) دقیقاً ادعایی است که باید آزموده شود نه فرض؛ گزینه ۲ (حذف timeoutها) مضر است.

## 3.8

**سؤال:** می‌خواهید حافظهٔ چند دستگاه را برای مدل بزرگ جمع کنید. مهم‌ترین قید اضافه چیست؟

**گزینهٔ منتخب:** `1` — ارتباط بین دستگاه‌ها و پشتیبانی runtime

**دلیل:** جمع کردن حافظهٔ چند دستگاه نیازمند تبادل activation و gradient (یا در inference، تبادل KV و بخشی از وزن) بین دستگاه‌هاست. اگر interconnect کند باشد (مثلاً PCIe در برابر NVLink)، سود حافظه با افت شدید throughput خنثی می‌شود. علاوه بر آن، runtime باید sharding را پشتیبانی کند (tensor parallel / pipeline parallel) — بدون آن، جمع حافظه بی‌فایده است. تکلیف در ۶.۸ همین را عددی می‌کند: انتقال ۲ GiB روی ۱۰ Gbit/s در برابر یک گام decode ۰٫۰۵ ثانیه. گزینه ۰ (حذف KV) غیرممکن؛ گزینه ۲ (جمع سادهٔ bandwidth) خطاست چون bandwidth تجمیعی خطی نیست؛ گزینه ۳ (برابری تضمینی با یک GPU) نادرست.

## 3.9

**سؤال:** مدل ۳۵ GiB وزن خام روی GPU با ۳۲ GiB VRAM انتخاب شده است. نتیجهٔ ظرفیت چیست؟

**گزینهٔ منتخب:** `0` — بدون offload یا تغییر representation جا نمی‌شود و KV نیز اضافه است

**دلیل:** وزن خام ۳۵ GiB از ظرفیت کل ۳۲ GiB بیشتر است، حتی پیش از کسر `reserved_gib` و پیش از افزودن KV cache و سربار. پس بدون offload (بخشی روی RAM) یا تغییر representation (کوانتیزهٔ بیشتر) جا نمی‌شود. توجه: اینجا «وزن خام» است نه «وزن Q4» — اگر Q4 بود ۳۵B×0.5≈۱۷٫۵ GB که جا می‌شد. قاعدهٔ تکلیف: `fits ⟺ total_gib <= capacity_gib - reserved_gib`. گزینه ۱ (چون MoE است وزن خام نادیده گرفته می‌شود) خطای سؤال ۲.۱ است — وزن همهٔ expertها باید در حافظه باشد؛ گزینه ۲ (با افزایش batch جا می‌شود) برعکس است؛ گزینه ۳ (چون bandwidth بالاست حتماً جا می‌شود) ظرفیت و پهنای باند را جابه‌جا می‌گیرد.

## 3.10

**سؤال:** تعداد TOPS یک NPU لپ‌تاپ بالا است. قبل از انتخاب برای LLM چه می‌سنجید؟

**گزینهٔ منتخب:** `2` — پشتیبانی مدل و operator و حافظه و runtime واقعی

**دلیل:** TOPS یک عدد اوج برای عملیات ماتریسی با دقت مشخص است؛ اما LLM به چهار چیز دیگر وابسته است: (۱) پشتیبانی operatorهایی که معماری مدل لازم دارد (attention با GQA، RoPE، softmax و …)، (۲) پشتیبانی خود معماری مدل در runtime، (۳) پهنای باند و ظرفیت حافظه — چون decode حافظه‌محور است (سؤال ۲.۱۱)، و (۴) بلوغ runtime و ابزارپذیری. یک NPU با TOPS بالا ولی پهنای باند کم و پشتیبانی operator ناقص، کندتر از یک CPU با پهنای باند کافی عمل می‌کند. گزینه ۰ (یکسان بودن TOPS با tok/s) همان اشتباه واحد است؛ گزینه ۱ (فقط تعداد هستهٔ CPU) هیچ‌کدام از این‌ها را نمی‌سنجد؛ گزینه ۳ (فقط TOPS تبلیغاتی) بدترین حالت است.

## 3.11

**سؤال:** بار ماهانه کم و نامنظم است و دادهٔ حساس وجود ندارد. چه مقایسه‌ای منصفانه است؟

**گزینهٔ منتخب:** `0` — TCO محلی شامل استهلاک و عملیات در برابر API با حجم واقعی

**دلیل:** با بار کم و نامنظم، هزینهٔ ثابت محلی (capex مستهلک‌شده + برق + عملیات + نگهداری) روی تعداد کم درخواست سرشکن می‌شود و per-request گران می‌شود. مقایسهٔ منصفانه باید همان حجم واقعی را در دو طرف بگذارد. `cost_scenarios.json` دقیقاً همین را مدل کرده: capex=3000، استهلاک ۳۶ ماه، ۱۶۰ ساعت/ماه، برق ۰٫۱۵ دلار/kWh، ops=۳۵ دلار/ماه، و نرخ API برابر ۱ دلار/میلیون input و ۳ دلار/میلیون output. سؤال ۶.۹ نقطهٔ سربه‌سر را از همین می‌سازد. گزینه ۱ (محلی همیشه رایگان) خطای رایج است — سرمایه و برق و عملیات رایگان نیستند؛ گزینه ۲ (API همیشه گران‌تر) تعمیم بی‌پایه است؛ گزینه ۳ (فقط برق در برابر API) capex و ops را نادیده می‌گیرد.

## 3.12

**سؤال:** برای انتخاب GPU اجاره‌ای جهت خدمت حساس، چه سندی علاوه بر ظرفیت لازم است؟

**گزینهٔ منتخب:** `1` — قیود محل داده و امنیت و نسخهٔ runtime و آزمون SLO

**دلیل:** در خدمت حساس، ظرفیت فقط یکی از شرط‌هاست. باید مشخص شود داده در کدام منطقهٔ جغرافیایی پردازش و ذخیره می‌شود (قیود محل داده)، چه کنترل‌های امنیتی روی میزبان اعمال می‌شود (دسترسی، شبکه، لاگ، رمزنگاری)، نسخهٔ دقیق runtime چیست و آیا پین شده است (بازتولیدپذیری)، و آیا SLO واقعی روی آن پیکربندی آزموده شده است. تکلیف در بخش ۱۲.۱ همین پنج قید را روی `deployment_cases.jsonl` می‌سنجد: `host`, `auth`, `remote_code`, `telemetry`, `redact`. گزینه ۰ (نام تجاری GPU) هیچ‌کدام را نمی‌دهد؛ گزینه ۲ (حافظهٔ لپ‌تاپ توسعه‌دهنده) بی‌ربط؛ گزینه ۳ (رتبهٔ عمومی مدل) ربطی به زیرساخت ندارد.
